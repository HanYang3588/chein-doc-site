维护与发布文档中心

内容所有权​

已有原稿保持原路径，docs-design/document-catalog.json 是迁移映射、实施状态和内容审核的唯一清单。站点生成于 website/.generated，编辑入口指回原稿。新增教程的原稿位于 website/product 与 website/reference。

publication_approved 记录内容核验，不代表批准生产发布。sensitivity_review.status=cleared-internal 仅许可内部完整站；不代表可以公开。历史设计、当前实现和 ADR 签署使用不同状态。

本地运行​

从仓库根目录执行：

pnpm --dir website install --frozen-lockfile
pnpm docs:check
pnpm docs:typecheck
pnpm docs:build
pnpm docs:serve

开发预览用 pnpm docs:dev。本工程拥有独立锁文件，不需要 Backend、Agent、数据库或管理前端运行。使用 Node 20+；CI 和容器采用 Node 24。

修改或新增原稿​

  1. 修改权威原稿，核对状态、代码证据、凭据、身份信息与图片；检查链接和 Mermaid。
  2. 在清单登记新源/目标；默认不发布，不能将未知文件自动复制进站点。
  3. 内容核验完成后明确传入路径执行 pnpm --dir website review -- <source...>。它更新审核 hash 与迁移报告；不要用它代替阅读核验。
  4. 运行 check/typecheck/build/smoke。生成流程会拒绝审核 hash 失效、重复目标、越界路径、缺失代码证据和凭据强特征。
  5. 用生产 serve 检查搜索、中文锚点、图片、关系图、深色与手机布局。

未批准的文档/图片不复制进正文、搜索或图谱；原稿链接显示“未发布资料”。代码证据链接指向 Git 仓库。页面不展示编辑日期、自动状态横幅或来源状态尾注；ADR 和历史记录中的事件日期保留。

API 与模块关系​

运行 node scripts/export-docs-openapi.mjs 导出四个 Edition 的脱敏 OpenAPI。它依赖 backend 的 locked 环境，使用本地导出配置、不执行 lifespan，不修改客户端或 Manifest。重新导出后审核契约并更新清单 hash，docs CI 消费快照，不连接业务服务。

参考页由快照自动生成，参数、请求与响应 Schema 可以下载完整 JSON。没有在线 Try it，不读取登录 Token。私有入口、示例、默认值和 server 地址不进入导出；字段类型、必填和约束保留。

模块关系由 Python 标准库 AST 读取 ModuleDefinition 字面量与 Edition YAML 成员。遇到无法解析的声明列入待解析，不导入业务应用；复杂 YAML Schema 需要同步升级读取器，不静默推断。

版本与搜索​

首发只有 current，不虚构发行版本。真实发布时由 release owner 执行 pnpm --dir website exec docusaurus docs:version <release>，只冻结 product 文档。reference 保持单一 current，生成流程禁止 reference_versions.json。版本文件由官方命令生成并提交，快照内容不随原稿生成覆盖。

本地搜索索引在 build 时生成，支持中文和英文。内部 noIndex 阻止搜索引擎索引，与 local search 的 forceIgnoreNoIndex 配合；它不是访问控制。引用和反向链接由 Markdown AST 生成，不根据共同标签编造引用。

独立静态部署​

CHEIN_DOCS_ORIGIN=https://docs.example.com CHEIN_DOCS_BASE_URL=/help/ pnpm docs:build
# 容器构建必须从仓库根目录提供白名单原稿
 docker build -f website/Dockerfile --build-arg CHEIN_DOCS_ORIGIN=https://docs.example.com --build-arg CHEIN_DOCS_BASE_URL=/help/ -t chein-docs:local .
 docker run --rm -p 127.0.0.1:8080:8080 chein-docs:local

example.com 是示例。先确认实际 origin、baseUrl 和现有网关/SSO，再部署内部制品。Nginx 非 root，仅提供静态文件，未知路径返回 404。HTML 与图谱使用短缓存，hash assets 使用长缓存；整站制品必须一起切换，不能混用旧搜索索引。

已在可信构建机生成并验收制品时，也可以使用 docker build -f website/Dockerfile.static --build-arg CHEIN_DOCS_BASE_URL=/help/ -t chein-docs:artifact website 仅打包静态制品，避免运行镜像包含 Node 工具链。baseUrl 必须与构建相同。

Docker 构建使用 whitelist context 阶段：仓库 .dockerignore 会排除私有 env、运行目录、node_modules 和上传；不要额外 COPY 私有配置。站点无需业务数据库迁移。

Actions 的 docs workflow 对 PR/push 执行检查；内部构建制品仅上传私有仓库。正式独立部署以手动 workflow_dispatch、受保护 docs-production Environment 和既有自托管 runner 为门禁；部署目标未配置时不会发布。Runner 需提供 CHEIN_DOCS_DEPLOY_ROOT 与现有静态服务，网关必须保护整个目录，包括搜索、JS、图片和下载。采用 release 目录与 current 符号链接原子切换；保留上一 release，回滚切换 current 到上一目录。

管理帮助入口​

构建管理前端时设置 CHEIN_DOCS_URL=https://实际域名/help/ 或同源 /help/。未配置或不安全地址隐藏菜单底部入口。开发环境允许 localhost HTTP；生产只接受 HTTPS 或同源 /help/。新窗口链接不附加 tenant/user/token。取消该配置并重新构建即可撤销入口，不涉及菜单表或数据库迁移。

中文写作规范​

  • 一篇文档解决一个主要问题，先说明用途、读者、适用范围和当前状态。
  • 按“准备条件 → 操作步骤 → 预期结果 → 失败处理 → 参考资料”组织教程；设计、交付和审计分别维护。
  • 使用一个一级标题，按层级连续使用二、三级标题。标题写清任务，正文一段只讲一个主题。
  • 说明文字使用中文；代码、命令、路径、协议字段、产品名和错误码保留原样。首次出现的缩写解释含义。
  • 表格用于比较，编号用于步骤。删除空泛评价和重复结论，明确区分事实、假设与待验收项。
  • 英文 ADR 可以翻译说明，但保留原状态、日期和决策含义；历史记录保留当时语境。

私有源码与 Actions 发布​

现有 .github/workflows/docs.yml 已提供构建和内部静态部署，无需公开源码仓库。PR 与 main push 执行构建检查；正式发布从默认分支手动运行 workflow，并将 deploy 设为 true。

发布前配置：

配置用途
私有 GitHub 仓库工作流仅在私有仓库上传内部制品和部署
docs-production Environment承载部署审核和环境变量
self-hosted runner 的 chein-docs 标签执行静态制品切换；应位于既有受保护服务环境
CHEIN_DOCS_ORIGIN实际 HTTPS origin，不含路径
CHEIN_DOCS_DEPLOY_ROOTrunner 上的绝对部署根目录
网关或 SSO保护 /help/ 下正文、搜索索引、图片与下载

当前工作流以 /help/ 制品部署，不会自动创建 GitHub Pages。源码私有与站点私有是两件事：GitHub Pages 默认可公开访问，即使源仓库私有；限制访问需满足对应账户和组织条件。参见 GitHub 官方建站说明与站点可见性说明。

对外产品展示应另行审核发布集合；完整技术站包含架构、代码路径和内部契约，不因去掉仓库链接就成为公开产品站。本文只准备本地制品与部署说明，不代表已执行远端发布。

图片与 PDF​

旧截图未完成身份审核，仍不发布。新截图先使用 scripts/save-dev-artifact.mjs 归档 RustFS；文档展示图经身份、业务数据和版权核对后，作为正式内容资产登记到清单。来源、拍摄日期与页面状态仅保存在资产审核元数据中。正文图注只解释界面和操作，不添加截图时间、拍摄过程或测试旁白；不能将空页面或未完成任务描述为成功案例。图片用成熟 zoom 插件；原图链接提供键盘替代，Esc 可退出缩放。

已有仓库没有 PDF，下载区保持为空；添加经审核 PDF 后放入 static/downloads 并登记资产，浏览器直接打开，避免复制一套 PDF viewer。构建检查禁止未登记的 static 资源。

维护个人与项目专栏​

原稿维护于 website/product/profile/，复用现有产品文档实例，使用独立的 profile 侧栏。顶部“个人与项目”和首页按钮进入完整履历；项目、公司、技术三个页面只维护分类索引，事实正文统一编辑 index.md，避免多份简历互相漂移。

本次根据用户提供的两页 PDF 整理，保留联系信息、证件照、教育、技能、公司经历、两个项目、证书与个人链接。原 PDF 不复制到下载区。年龄、经验年限、任职起止及量化成果保留原简历口径，不自动推算；Agent 为用户明确提出的发展方向，不补造 Agent 项目或工作成果。联系方式和照片属于用户授权导入的个人信息，本站仍为内部发布范围，公开投递前需由本人确认展示范围。

新增或修改资料后，更新发布清单，核对事实和联系方式，再显式执行 review 及文档验证。维护正文时保持原有章节锚点；改名需同步修复三个分类页。

排版调研参考 ResumeSample、中文程序员 Markdown 简历和 stick-i Markdown 模板。采用清楚的模块标题、时间、职责、技术方案与结果层次，自行编写本站样式；未复制模板源码、他人履历或引入额外依赖。
