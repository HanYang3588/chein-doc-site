部署与回滚设计

先阅读架构、安全与 API、技术选择和验证记录。服务构建、启动与离线命令见 运行手册（未发布资料）。

服务位于 services/chein-reasoner，单 Maven 模块，不创建第二套管理后台。Compose 为可选覆盖 compose.reasoner.yml，不暴露 Java 主机端口，仅 Backend 可访问内部服务。容器非root、只读rootfs、私有任务volume、tmpfs、cap_drop ALL、no-new-privileges、pids与1CPU/2GiB预算。主/子JVM堆总量小于容器内存；每任务进程超时后必须回收。

Nacos 默认可关闭以离线运行。启用后复用已有 server/namespace/CHEIN group，服务名 chein-reasoner，显式发布实例IP/端口，启动读取配置失败则拒绝启动，运行失联不放宽授权。不要自动修改正常 Nacos 目录或 Higress 路由；提供示例，由维护者按环境发布。Higress仅将 /api/v1/ontology/reasoner 路由到现有Backend，Java不直接接受浏览器；现有登录Session和授权由Backend逐请求验证。

Ubuntu 无外网：在受信任联网构建机上 Maven verify / dependency:go-offline，打包 Maven repository、源码、许可证和 SBOM；离线 Maven -o 验证后构建镜像或直接 docker save/docker load 传输已构建镜像。核验SHA256，不在离线服务器启动时下载HermiT/n10s依赖。密钥仅来自部署Secret或受限Nacos配置，不进镜像/构建args/仓库。

回滚：先关闭 Backend reasoner enabled，停止新提交，再取消/等候计算服务；保留私有卷和备份，旧未完成任务重启后失败关闭而非自动重跑。无PG schema迁移，原Ontology接口兼容。已经采用新契约的生成客户端随源契约一起回退；不删除历史计算审计/结果来掩盖状态。

正常配置与启用顺序​

  1. 部署 services/chein-reasoner 的已验证 JAR/镜像及独占私有卷，Java 配置 REASONER_PUBLIC_KEY；它必须对应 Backend 的 reasoner 专用 Ed25519 私钥或既有 AGENT_DELEGATION_PRIVATE_KEY。私钥只留在 Backend 部署 Secret。密钥轮换当前需要协调重启，不支持多公钥无缝轮换。
  2. 选择正常运行网络地址。Compose 内部使用 http://reasoner:8091，显式允许内部 HTTP；生产跨主机使用 TLS/mTLS。合并 deploy/nacos/reasoner-backend.patch.yaml.example 到现有 Backend runtime 配置，确认 URL/密钥后将 enabled 改为 true。默认关闭，关闭不会触发其他引擎补偿执行。
  3. 如启用 Nacos，填写现有 Server 地址、Namespace、凭据、当前容器可达 IP，Group 为 CHEIN；按需发布 chein-reasoner-runtime.properties，开启启动配置后缺配置会拒绝启动。只读固定白名单，无热更新，参数变化重启 reasoner。Backend 复用固定内部 URL，Nacos 用于发现/治理，不在请求中根据客户端参数发现任意服务。
  4. Backend 重启加载新增配置；Java 服务新增启动。不要求重启 Neo4j、ERP、Agent、PG、Redis；前端仅生成 API 客户端，没有新增界面。启用前正常 Backend 仍可使用原接口。
  5. Higress 配置下述入站边界，使用已登录会话提交本人有界 OWL 验证。测试与正常运行使用相同配置项，不设置另一套测试连接。

Higress 配置核对​

deploy/higress/reasoner-route.yaml.example 使用官方 McpBridge resource backend 和 destination 注解；普通 Kubernetes service backend 会忽略这条服务发现路由。复用已经连接 Nacos 的 McpBridge，目的地址只指向 Backend。Group/Namespace/端口按实际发现结果替换；Java 不增加公网 Ingress。

reasoner-plugins.yaml.example 提供局部 WasmPlugin：AUTHN ext-auth 先调用 Backend /api/v1/ontology/reasoner/auth，验证现有登录 JWT、UserSession、当前租户/成员；所有业务路由仍独立验证模块和资源。认证失败/依赖错误关闭。认证响应写入固定 x-chein-reasoner-budget=shared，随后 key-rate-limit 按该值做本地预算，客户端不能靠换头规避。示例每秒5次是网关工作进程本地配额，不是租户配额或分布式配额；Java 的单 Worker/有限队列仍是最终资源边界。认证前匿名洪泛复用部署已有连接/WAF保护，不把该业务限流宣称为认证服务的抗洪泛方案。

插件仅匹配 dedicated Ingress，不使用全局 defaultConfig，避免影响其他接口。官方 Kubernetes 匹配名为 namespace/ingress；本次 Docker standalone controller 实测路由 ID 为纯 ingress 名，需移除命名空间前缀才能生效。部署后必须验证实际 Wasm route config、匿名401、认证依赖故障503和限流429；Backend 的401不能单独证明网关插件已执行。插件地址/版本对应当前安装的 plugin-server，离线环境提前准备 wasm，不复制本地测试的 localhost 地址。生产 K8s 场景尚未演练。

参考：官方 Nacos 路由、插件作用域、Key 本地限流。Docker All-in-One 仅用于本次隔离验证，不作为生产推荐拓扑。

发布前门禁​

内部网络/传输保密、卷权限/加密备份、日志采集和可选 OTLP 端点由现有运维设施提供。REASONER_TRACING_ENABLED=true 才开启应用 Trace；直接 Java 使用 Spring Boot 的 MANAGEMENT_OTLP_TRACING_ENDPOINT，Compose 使用 REASONER_OTLP_TRACING_ENDPOINT 配置实际接收地址（含 /v1/traces）。只传 metadata，不传 OWL。完整依赖和镜像扫描、签名、LGPL 对应源码及替换义务审阅、Ubuntu 目标架构离线演练、生产网关/密钥轮换与团队 ADR 签署仍须完成，见验证记录。不要将本地测试通过写成已经上线。
