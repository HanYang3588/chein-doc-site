对账与数据一致性（Reconciliation）

状态：操作与事实说明（以 application/reconciliation.py、reconciliation_routes.py 为准）。

适用范围：库存与结算金额的租户内一致性自检、健康状态与差异定位。

1. 做什么检查​

对账是只读检查，不会自动修复数据。它只跑两个对比：

检查期望值来源实际值来源差异记录
库存（stock）stock_ledger 按 (product_id, warehouse_id) 汇总 delta_quantitystock_balance.quantitystock_difference_count
结算（settlement）finance_payment_item + finance_receipt_item（仅统计已审批表头）的 ABS(settlement_signed) + discount_allocated（仅 purchase_in / sale_out）按来源汇总来源单据 purchase_in / purchase_return / sale_out / sale_return 的 settled_amountsettlement_difference_count

库存检查会同时发现"有余额无流水"和"有流水无余额"两类差异（键取并集）。 结算检查同理：期望集合与实际集合取并集，任一侧缺失都算差异。

2. 触发方式​

方式入口权限triggered_by
每日计划任务计划 erp.reconciliation.daily（间隔 24 小时，由平台按租户枚举调用）平台调度NULL
手工触发POST /api/v1/erp/reconciliation-runs（需要 Idempotency-Key 头）erp:reconciliation:execute当前用户 id
查看最近一次GET /api/v1/erp/reconciliation-runs/latesterp:reconciliation:read-

设计意图是同一租户同一时刻只跑一个对账，但代码并未强制（没有唯一索引或 advisory lock）：status = running 只是写库时的初始值，通常在同一事务内就变为 passed / failed。 如果并发触发，会写出多条 reconciliation_run，判断当前状态时按 started_at 取最新一条。

另外每小时会执行计划 erp.command_receipt.cleanup，清理 expires_at 已过期且 status = completed 的幂等凭证（command_receipt）。

3. 结果写在哪里​

  • erp.reconciliation_run：每次运行的快照
    • status：running / passed / failed
    • stock_difference_count、settlement_difference_count
    • summary_json：差异样本，stock_difference_samples 与 settlement_difference_samples 各最多 20 条（库存为 {product_id, warehouse_id}，结算为 {source_type, source_document_id}；这里只存样本，完整差异条数看两个 count 字段）
    • started_at、completed_at、triggered_by
  • erp.erp_setting（按租户一行）：
    • integrity_status：healthy（无差异）或 degraded（有差异）
    • last_reconciled_at、version（每次对账 +1）
  • Outbox 事件：有差异时发 erp.reconciliation.failed （平台注册了消费方 register_reconciliation_failure_consumer）。
  • 指标：erp_reconciliation_differences{kind="stock"|"settlement"} 记录最近一次的差异数 （Gauge，不是累计值）。

4. 排查：发现差异后怎么做​

第一步：确认差异范围

SELECT status, stock_difference_count, settlement_difference_count,
       started_at, completed_at, summary_json
FROM erp.reconciliation_run
WHERE tenant_id = '<tenant>'
ORDER BY started_at DESC LIMIT 5;

第二步：库存差异定位（余额与流水不平的商品+仓库）

WITH ledger AS (
  SELECT product_id, warehouse_id, SUM(delta_quantity) AS total
  FROM erp.stock_ledger WHERE tenant_id = '<tenant>'
  GROUP BY product_id, warehouse_id
)
SELECT COALESCE(b.product_id, l.product_id) AS product_id,
       COALESCE(b.warehouse_id, l.warehouse_id) AS warehouse_id,
       b.quantity AS balance, l.total AS ledger_total
FROM erp.stock_balance b
FULL JOIN ledger l
  ON l.product_id = b.product_id AND l.warehouse_id = b.warehouse_id
WHERE b.quantity IS DISTINCT FROM COALESCE(l.total, 0);

第三步：结算差异定位（来源单据的 settled_amount 与收付款明细合计不符）

SELECT s.source_type, s.source_document_id, s.settled_amount AS document_settled,
       COALESCE(t.applied, 0) AS applied_from_finance
FROM (
  SELECT 'purchase_in' AS source_type, id AS source_document_id, settled_amount, tenant_id FROM erp.purchase_in
  UNION ALL SELECT 'purchase_return', id, settled_amount, tenant_id FROM erp.purchase_return
  UNION ALL SELECT 'sale_out', id, settled_amount, tenant_id FROM erp.sale_out
  UNION ALL SELECT 'sale_return', id, settled_amount, tenant_id FROM erp.sale_return
) s
LEFT JOIN (
  SELECT item.source_type, item.source_document_id,
         SUM(ABS(item.settlement_signed)
             + CASE WHEN item.source_type IN ('purchase_in','sale_out') THEN item.discount_allocated ELSE 0 END) AS applied
  FROM erp.finance_payment_item item
  JOIN erp.finance_payment p ON p.id = item.finance_payment_id
       AND p.status = 'approved' AND p.tenant_id = item.tenant_id
  WHERE item.tenant_id = '<tenant>'
  GROUP BY item.source_type, item.source_document_id
  UNION ALL
  SELECT item.source_type, item.source_document_id,
         SUM(ABS(item.settlement_signed)
             + CASE WHEN item.source_type IN ('purchase_in','sale_out') THEN item.discount_allocated ELSE 0 END)
  FROM erp.finance_receipt_item item
  JOIN erp.finance_receipt r ON r.id = item.finance_receipt_id
       AND r.status = 'approved' AND r.tenant_id = item.tenant_id
  WHERE item.tenant_id = '<tenant>'
  GROUP BY item.source_type, item.source_document_id
) t ON t.source_type = s.source_type AND t.source_document_id = s.source_document_id
WHERE s.tenant_id = '<tenant>'
  AND s.settled_amount <> COALESCE(t.applied, 0);

第四步：判定处理方式

  • 差异来自已反向但未清干净的操作：优先用业务接口补做反向/重做，不要直接 UPDATE。
  • 差异来自绕过应用的直接写库：属于数据事故，需要按 stock_ledger / document_action_log 重建事实并升级处理；不要用 UPDATE 掩盖（stock_ledger、 document_action_log 本身被应用层禁止修改）。
  • 修复后再次触发对账，确认 erp_setting.integrity_status 回到 healthy。

5. 常见误解​

  • 对账通过 ≠ 业务金额正确：它只验证"流水与余额一致""核销明细与单据字段一致"， 不校验定价、折扣合理性、往来方是否正确。
  • 对账不会修改数据：run_reconciliation 只写 reconciliation_run 与 erp_setting。
  • degraded 不是错误码：它只是最近一次对账的结果，接口本身仍会正常返回列表数据。
