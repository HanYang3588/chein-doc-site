Token 计费实现复核与优化设计

  • 状态：Proposed（复核结论与待实施优化；未实现）
  • 对照基线：Token 计量、计费与分级额度设计、实施交付
  • 复核方式：阅读 agent/src/chein_agent/usage/、api.py、decision.py、迁移 0012/0013 与前端 pages/agent/context-usage.tsx、modules/platform/agent/usage/；运行 ruff check（usage 与两份测试，通过）及前端 vitest（3 文件 18 用例通过）。未运行需一次性 PostgreSQL 的 Agent 数据库测试，未验证 Higress、真实供应商与远端 CI。

1. 结论​

核心架构按设计落地：账本、版本价格、计数器、租户→部门→用户额度、observe/soft/hard、Agent 调用点覆盖与 Backend BFF 均已存在。但有两类问题需要优化：

  1. 对话页 Token 统计显示错误、来源跳变。
  2. 账本写入在高并发下可能静默丢失，而计费账本不应有静默丢失路径。

2. 需求对照​

需求状态证据与说明
统一账本与版本价格达成migrations/0012_token_billing.sql，usage/recorder.py 同事务写账本与计数器
租户/部门/用户层级、取最严达成（待负载验证）usage/control.py evaluate、status
日/月周期与 observe/soft/hard达成control.py、策略 CRUD 含版本冲突与审计
hard 计数器故障失败关闭达成status 在 enforce 且 hard 时返回 503
调用点覆盖（主模型、子 Agent、摘要、决策、图片、视频、语音）基本达成harness.py、decision.py、images.py、context.py
写入不丢账未达成见 P0-1
对话页用量准确展示未达成见 P0-2、P1-1～P1-3
Higress L1 熔断仅示例外部门禁，见 §6

3. 缺陷清单​

P0-1 账本写入可能静默丢失​

位置：usage/recorder.py、usage/repository.py::lock_tenant。

  • record_usage 使用 asyncio.timeout(0.25)，无重试，异常被吞掉，且无丢失计数。
  • 每次写入取租户级 advisory lock，同租户的并行子 Agent 与多用户调用被串行化；排队超过 250 ms 即丢账。
  • reasoning_tokens > output_tokens 或 cached_input_tokens > input_tokens 时 cost_micro 抛 ValueError，整条调用丢失，而不是钳制并标记。
  • 价格查询位于热事务内，进一步拉长持锁时间。

P0-2 对话页角色与模型标签错误​

位置：repository.py::report、pages/agent/context-usage.tsx（约 126 行与 153 行）。

  • 线程报告以 group_by=model 查询，SQL 以 model_id || ' / ' || role 拼成单个 key，不返回 role 与 model_id 列。
  • 前端使用 r.role || 'auxiliary' 与 model_id: r.key，所以所有行显示为“辅助”，模型名显示为 “qwen / main”，主/摘要/子 Agent 区分丢失。

P1-1 统计来源跳变与闪烁​

  • ledgerActive 依赖 ledger?.mode，请求返回前为 undefined（含 300 ms 防抖），先显示旧指标再切换。
  • 请求失败时 SessionUsageProvider 置为 undefined，静默回退到旧 context.usage 数据；两者口径不同（旧口径仅主模型），数字会突变且无提示。
  • 刷新键为 run_id:sequence:running，账本落库晚于旧计数，展示滞后。
  • 草稿线程没有 activeThreadId，不请求账本。

P1-2 口径混杂​

账本汇总包含图片、视频、语音等全部 usage_kind，页面却按“LLM Token”展示；cache_usage_calls 被强制设为总调用数。

P2 可观测性与一致性​

  • 无丢账计数、写入耗时、锁等待指标与告警。
  • 无账本与 context.usage 的对账，无法发现口径偏差。
  • 报告接口行数上限 1001，超限行为需明确提示。

4. 目标设计​

4.1 持久写入（P0-1）​

  1. 增加 Agent 自有的本地持久 spool（PostgreSQL 表 agent_usage_spool，租户 FORCE RLS，仅含数值与引用）：热路径先写 spool（单行 insert，无租户锁），由后台 flusher 在批量事务中写账本与计数器，幂等键沿用 invocation_id。
  2. 取消热路径 250 ms 超时丢弃：失败写入进入有界重试，仍失败则计入 usage_write_dropped_total 并输出结构化错误日志。
  3. 租户锁改为按 (tenant, 计数器键) 分片或在 flusher 内批量加锁，缩短持锁时间；价格按版本缓存于进程内，缓存键含价格版本，不缓存授权。
  4. 非法子集（reasoning>output、cached>input）钳制到合法值并在账本行打 anomaly 标记，不抛错、不丢账。
  5. 不改变既有行为：hard 准入仍以计数器为准，计数器故障失败关闭规则不变。

4.2 会话用量接口与展示（P0-2、P1）​

  1. 报告接口新增 group_by=model_role，显式返回 model_id、role、usage_kind；保持旧 key 向后兼容一个版本。
  2. 新增 GET me/usage/session（按本人 thread_id）返回：LLM 汇总（仅 usage_kind=llm，含 main/summary/subagent/decision 拆分）、媒体行（图片/视频/语音）单列、数据新鲜度（as_of、pending）。
  3. 前端状态机：loading → ledger | unavailable，禁止静默回退旧数据；失败时显示“用量暂不可用”并保留上一次成功值，标注时间。
  4. 去掉对 ledger?.mode 的闪烁依赖：模式从预取的预算状态获得，首屏不出现临时 chip。
  5. 运行中使用旧 context.usage 仅作实时上下文环（语义为上下文占用），累计用量一律取账本，两者标签区分。
  6. 草稿线程不请求账本，显示零值而非错误。

4.3 对账与观测（P2）​

  • 指标：usage_write_dropped_total、usage_spool_lag_seconds、usage_write_seconds、usage_anomaly_total。
  • 对账脚本（扩展 reconcile_token_usage.py）对比线程级账本与 context.usage 累计，差异超阈值告警。

5. 验收标准​

  1. 并发 50 个同租户写入且人为注入 300 ms 数据库延迟，账本行数等于调用数，丢失计数为 0。
  2. 注入 reasoning>output 数据，写入成功且带 anomaly。
  3. 对话页：主、摘要、子 Agent 各自标签与模型名正确；首屏无 chip 闪烁；接口失败显示不可用提示而不是切换口径。
  4. 含图片/视频的线程，LLM Token 汇总不含媒体行。
  5. 既有 usage、control、Backend 与前端测试全部保持通过；新增测试覆盖上述场景及跨租户/跨用户负向。

6. 仍未验证的外部门禁​

Higress 真实插件摘要与头部泄漏、取消流 usage、供应商账单对账、RAGFlow 内部 usage、通知送达与压测、远端 CI。本稿不改变这些状态。

7. 兼容与迁移​

  • 新增 spool 表需新 migration（接在 0013 之后，含 down），先于代码启用；flusher 关闭时回退为直接写入。
  • 报告接口新增字段向后兼容，key 保留至下一个版本。
