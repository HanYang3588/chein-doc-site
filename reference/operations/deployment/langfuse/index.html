Langfuse v4 部署、账户配置与故障复盘

状态：用户提供的 2026-10-13 复盘确认已成功登录 Langfuse，并记录 PostgreSQL 迁移完成。本文未连接服务器复验；ClickHouse 最终权限、Redis/S3 配置、trace 落地和 Chein Agent 接入仍待验证。

主流程复用已有 PostgreSQL、Redis、ClickHouse 和 S3 兼容存储；保留新建 ClickHouse 的备选方案。

1. 部署范围​

按本次部署记录，只新增 Langfuse Web、Langfuse Worker 两个常驻容器，复用已有 ClickHouse。PostgreSQL 使用独立数据库和账户，RustFS 使用独立私有 bucket 和应用密钥；Redis 复用现有密码，预留独立 logical DB 和 key prefix。

组件操作数据与用途
Langfuse Web新部署管理界面、认证、SDK 接收入口
Langfuse Worker新部署异步处理观测数据与后台任务
ClickHouse复用已有实例，核对版本、权限与 UTC 时区观测数据与分析查询；HTTP 与 Native TCP 分别配置
PostgreSQL复用实例，新建 langfuse 数据库Langfuse 用户、组织、项目和配置
Redis满足下文条件时复用现有密码队列与缓存，预留独立 logical DB 和 key prefix
RustFS经兼容性验收后复用原始事件与可选媒体，独立私有 bucket
Elasticsearch本方案不配置Langfuse 不使用 ES，ES 不能替代 ClickHouse

部署独立于 Chein Compose，不加入 Edition，也不修改管理后端迁移。Langfuse 只提供辅助观测；业务状态、授权和 checkpoint 继续以 Agent 架构 为准。

账户与存储准备完成后，依次执行：填写中间件参数 → 拉取 Web/Worker 镜像 → 核对 ClickHouse 并迁移 → 启动 Web/Worker。历史问题与恢复边界见本次故障复盘。

场景仓库模板常驻服务
已有 ClickHouse（本文主流程）compose.external.ymlWeb、Worker；全部中间件外置
需要新建 ClickHousecompose.ymlWeb、Worker、ClickHouse；额外步骤见第 7.5 节

仓库模板仍固定 Langfuse Web/Worker 为 4.56.0；两者必须同版本。用户部署记录使用 Docker Hub 的 langfuse/langfuse:4 与 langfuse/langfuse-worker:4，尚未提供对应具体版本/digest，不能把该部署记为已验证 4.56.0；维护已有实例时先记录现有镜像，不直接换版本。新建 ClickHouse 的备选模板使用 26.4 系列。官方 v4 要求 PostgreSQL ≥15、Redis ≥7、ClickHouse ≥25.12；推荐 PostgreSQL 16、Redis 7.2、ClickHouse 26.4。先核对已有版本，低于要求时先处理兼容性，不在本操作中直接升级共享实例。版本依据、4.56.0 发布记录。

复用中间件不会自动增加副本或故障转移。官方将单容器 ClickHouse 标为开发用途的社区支持方案；本次同机单容器部署不构成生产高可用证据。ClickHouse 支持边界。

逐项填入自己的值。下文 *.example.com 和密码占位符不能直接使用。

网络约定：

  • 宿主机只绑定 127.0.0.1:3000（Web）、127.0.0.1:3030（Worker 健康检查）。最终入口通过已有反向代理或 VPN 访问。
  • 同机 ClickHouse 优先通过共享 Docker 网络和服务名访问；若使用宿主机 LAN IP，核对 8123/9000 端口映射和防火墙。备选新建模板不发布这两个端口。共享网络本身不是鉴权边界。
  • 容器内 localhost 指当前容器；已有 PG/Redis/RustFS 在同一用户自定义网络时填服务名，否则填可达 DNS/IP。
  • 示例内部 HTTP/Redis 明文连接假定同机或可信私网；跨不可信网络时应配置相应 TLS。不要通过关闭证书校验解决连接失败。

3. PostgreSQL：创建独立数据库和两个账户​

以下 SQL 只用于 Langfuse 的新数据库，不是 Chein 的业务迁移。采用“迁移账户一次性执行 + 常驻容器只使用运行账户”，不向 Chein API、Agent 或 Langfuse 常驻容器注入数据库 owner 密码。

3.1 在 DataGrip 中连接并创建账户、数据库​

在 DataGrip 中使用现有 PG 管理账户连接目标实例，连接配置的 Database 填 postgres，打开 SQL 控制台。以下步骤需要管理账户具备创建角色、为其他角色创建数据库及授权的权限；不要使用 Chein 的运行账户。

将控制台事务模式设为 Tx: Auto（自动提交），按下面各代码块依次执行。不要把整节 SQL 放进 BEGIN / COMMIT，也不要一次选中整节执行。DataGrip 事务模式。

先检查：

SHOW server_version;
SELECT datname FROM pg_database WHERE datname = 'langfuse';
SELECT rolname FROM pg_roles
WHERE rolname IN ('langfuse_migrator', 'langfuse_runtime');

数据库和账户已存在时先确认所有者和用途，不覆盖、不删除，也不要重跑对应的 CREATE。下面是全新安装步骤，要求 PostgreSQL ≥15。

在密码管理器中生成两个不同的强随机密码，推荐各用 64 位 hex，替换下面两个 REPLACE_WITH_... 占位符后执行。CREATE ROLE ... LOGIN 创建的就是可登录用户，不需要再执行 CREATE USER。SQL 中的密码填写原值；如果包含单引号，写成两个单引号 ''。CREATE ROLE 语法。

CREATE ROLE langfuse_migrator LOGIN
  PASSWORD 'REPLACE_WITH_MIGRATOR_PASSWORD'
  NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS;
CREATE ROLE langfuse_runtime LOGIN
  PASSWORD 'REPLACE_WITH_RUNTIME_PASSWORD'
  NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS;

密码保存到密码管理器，并分别填入 migration.env 和 langfuse.env 的对应连接串；URL 中若有保留字符须 percent-encode。DataGrip 会保存执行历史，含真实密码的 SQL 不保存到仓库、不共享；执行后按本地凭据管理要求清理相关历史。DataGrip 查询历史。

单独选中并执行下面这一条；CREATE DATABASE 不能在事务块中运行。若报 cannot run inside a transaction block，先结束当前事务并确认 Tx: Auto，再单独执行。PostgreSQL 限制。

CREATE DATABASE langfuse OWNER langfuse_migrator;

创建成功后，继续在连接 postgres 的管理账户控制台执行：

REVOKE ALL ON DATABASE langfuse FROM PUBLIC;
GRANT CONNECT ON DATABASE langfuse TO langfuse_runtime;
ALTER DATABASE langfuse SET timezone TO 'UTC';

3.2 在 DataGrip 中切到新数据库授权​

在 DataGrip 中复制管理账户的数据源，把连接配置的 Database 改为 langfuse，连接后打开新的 SQL 控制台。先执行下面的检查，确认结果为 langfuse 和管理账户后，再执行授权 SQL。仅切换 schema 不会切换 PostgreSQL 数据库；这里不使用 psql 专用的反斜杠命令。

SELECT current_database(), current_user;
REVOKE ALL ON SCHEMA public FROM PUBLIC;
GRANT USAGE, CREATE ON SCHEMA public TO langfuse_migrator;
GRANT USAGE ON SCHEMA public TO langfuse_runtime;

ALTER DEFAULT PRIVILEGES FOR ROLE langfuse_migrator IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO langfuse_runtime;
ALTER DEFAULT PRIVILEGES FOR ROLE langfuse_migrator IN SCHEMA public
  GRANT USAGE, SELECT ON SEQUENCES TO langfuse_runtime;

GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public
  TO langfuse_runtime;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public
  TO langfuse_runtime;

Langfuse 在所选数据库的 public schema 建表，不能把 URL 指向 Chein 的 app 数据库。上面的默认权限确保官方迁移创建的后续表也能由 runtime 访问；迁移始终以 langfuse_migrator 执行。PG 配置依据。

在 PG 网络 ACL / pg_hba.conf 中只允许部署机访问，并限制这两个角色只能连接 langfuse。PostgreSQL 的其他数据库可能默认允许 PUBLIC CONNECT，所以“新建账户”本身不保证不能连其他库。自管 PG 可在宽泛放行规则之前配置：

hostssl langfuse langfuse_migrator,langfuse_runtime DEPLOY_HOST_IP/32 scram-sha-256
host    all      langfuse_migrator,langfuse_runtime 0.0.0.0/0 reject
host    all      langfuse_migrator,langfuse_runtime ::/0      reject

DEPLOY_HOST_IP 应为 PG 实际看到的客户端地址（可能是容器网段或 NAT 出口）。先核对再 reload；这些规则只针对新角色，不改业务角色。托管 PG 用供应商等价控制。若受控同机网络无 TLS，明确将示例 hostssl 改为 host、连接串 sslmode=require 改为 disable；不要默认现有 PG 支持 TLS。

验收：用 runtime 连接 langfuse，SHOW timezone 返回 UTC；用它连接业务数据库必须拒绝，且 has_schema_privilege(current_user, 'public', 'CREATE') 返回 false。

3.3 迁移后检查表所有权与运行权限​

在 DataGrip 的 langfuse 管理连接中执行：

SELECT current_database(), current_user;
SELECT schemaname, tablename, tableowner
FROM pg_tables
WHERE schemaname = 'public'
ORDER BY tablename;

SELECT has_schema_privilege('langfuse_runtime', 'public', 'USAGE') AS runtime_usage,
       has_schema_privilege('langfuse_runtime', 'public', 'CREATE') AS runtime_create;

SELECT t.schemaname, t.tablename, p.privilege AS missing_privilege
FROM pg_tables AS t
CROSS JOIN (VALUES ('SELECT'), ('INSERT'), ('UPDATE'), ('DELETE')) AS p(privilege)
WHERE t.schemaname = 'public'
  AND NOT has_table_privilege(
    'langfuse_runtime', format('%I.%I', t.schemaname, t.tablename), p.privilege
  );

runtime_usage 应为 true，runtime_create 应为 false，最后一条应无缺失权限。迁移创建的 Langfuse 表应由 migrator 拥有；遗留表由其他角色拥有时，由 DBA 先核对对象用途再调整所有者。schema 的 CREATE 权限不能替代修改已有表所需的所有权。PostgreSQL ALTER TABLE。

缺权限时按第 3.2 节补授权已有表和序列，再检查默认权限。默认权限只影响指定创建者的后续对象，不会补授权已有表或其他角色创建的表。默认权限规则。GRANT ... ON ALL TABLES 也覆盖 _prisma_migrations；若另行撤销该迁移表的写权限，将其从业务表检查中排除并验证应用行为。

4. Redis：复用现有密码，使用独立 DB 和前缀​

本方案适用于已有 requirepass 密码、未创建专用 ACL 用户的 standalone Redis，不新增用户或修改现有密码。Redis ≥6 仍有默认用户 default；只提供密码时就是以该用户认证。这里使用的是编号 logical DB（例如 DB 12），不是 RustFS 的 bucket。Redis 认证依据。

必须 Redis ≥7 且 maxmemory-policy=noeviction。 Redis logical DB 不隔离内存、淘汰策略或故障，DB 12 不能解决共享实例的策略冲突。若已有实例是业务 LRU 缓存且不能整体改成 noeviction，本方案的 Redis 复用前提不成立，需要另部署专用 Redis/Valkey；不要直接 CONFIG SET 改业务实例。官方要求。

4.1 用现有密码检查实例​

以下 Shell 示例用 Bash。交互读取现有 Redis 密码，避免命令行明文参数；不指定 --user：

read -r -s -p 'Existing Redis password: ' REDISCLI_AUTH; echo
export REDISCLI_AUTH
redis-cli -h redis.example.com -p 6379 INFO server
redis-cli -h redis.example.com -p 6379 INFO keyspace
redis-cli -h redis.example.com -p 6379 CONFIG GET maxmemory-policy
redis-cli -h redis.example.com -p 6379 CONFIG GET databases
redis-cli -h redis.example.com -p 6379 INFO persistence
redis-cli -h redis.example.com -p 6379 -n 12 PING
unset REDISCLI_AUTH

TLS 实例加 --tls --cacert /path/to/ca.pem，后续 URL 改成 rediss://，设置 REDIS_TLS_ENABLED=true；私有 CA 按官方 Redis 配置挂载并指定 REDIS_TLS_CA_PATH。

核对配置和既有应用后预留一个空闲 DB，本文用 12 举例。DB 号从 0 开始，CONFIG GET databases 必须大于 12；最后一条应返回 PONG。如果选择其他 DB，同步修改检查命令与下文连接串。INFO keyspace 中暂时为空不证明没人使用，还要查已有配置。若托管实例禁止 CONFIG GET，从管理控制台确认等价参数。建议开启 AOF 并评估 appendfsync everysec，Redis 这里承载队列，不能按可随意清空的缓存运维；持久化策略由现有实例管理员在原配置中落实。

4.2 配置 Langfuse 连接​

在 langfuse.env 中填写现有 Redis 密码，用户名留空（redis:// 后紧接冒号），不执行 ACL SETUSER：

REDIS_CONNECTION_STRING=redis://:REPLACE_WITH_EXISTING_REDIS_PASSWORD@redis.example.com:6379/12
REDIS_KEY_PREFIX=chein-langfuse
REDIS_TLS_ENABLED=false

密码中的 @、:、/、#、% 等 URL 保留字符须 percent-encode，不能直接粘贴原值。Langfuse 连接串格式。

独立 DB 和 prefix 用于避免 key 冲突，不提供访问权限隔离：持有同一密码的应用仍可切换到其他 DB；本方案不能验收为“禁止跨 DB 访问”。共享密码轮换时必须协调所有使用方，不能只改 Langfuse。

prefix 在冻结版本中同时用于缓存与 BullMQ 队列，见 4.56.0 Redis 实现。多套 Langfuse 必须使用不同 prefix，Web/Worker 必须使用相同连接串和 prefix。

若实际是 Redis Cluster/Sentinel，停止套用本节 URL 模板。 Cluster 不支持 DB 12，应采用官方 cluster 节点配置和带 hash tag 的队列前缀；Sentinel 使用其专门变量与主节点名称。本文模板仅覆盖 standalone Redis，不通过伪装单节点绕过拓扑要求。

5. RustFS：bucket、专用密钥与权限​

RustFS 按 S3 兼容 API 复用；Langfuse 官方对其他 S3 兼容实现提供社区支持，没有在所核对页面单独认证 RustFS。本方案是基于协议兼容性的选择，必须通过本节与第 9 节的实测。Langfuse S3 配置、RustFS S3 API。

5.1 管理员创建两个私有 bucket​

在 RustFS 控制台创建 langfuse-events、langfuse-media，关闭匿名访问，保持 Public Access Block。不要使用已有业务 bucket，不添加公共读策略。

初期不开启 batch export，因此无需第三个 bucket。先不设置自动过期：待确认 ingestion 最大延迟、故障恢复窗口及数据保留要求后，再配置 lifecycle；未消费事件提前删除会导致观测丢失。

5.2 创建专用用户/服务账户​

在 RustFS 的 IAM / 用户 / Policies 页面创建 langfuse 专用用户，把下面的 IAM 身份策略保存为 langfuse-storage 并绑定给该用户。再从该用户创建应用 Access Key / Secret Key，记录到密码管理器；不同 RustFS 版本界面名称可能不同，以实际 IAM 功能为准。

不要把此 JSON 当成 bucket 公共策略，也不要把 RustFS root key 下发给 Langfuse。服务账户继承父用户权限，应选择专用父用户并限制范围。RustFS IAM、身份策略格式。

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:ListBucket", "s3:GetBucketLocation"],
      "Resource": [
        "arn:aws:s3:::langfuse-events",
        "arn:aws:s3:::langfuse-media"
      ]
    },
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject", "s3:DeleteObject"],
      "Resource": [
        "arn:aws:s3:::langfuse-events/events/*",
        "arn:aws:s3:::langfuse-media/media/*"
      ]
    }
  ]
}

对象删除权限用于本 bucket 的清理与人工验收；不授权创建/删除 bucket、管理用户、访问业务对象。大文件 multipart tracing 不在首期范围，确有需要时先验证 RustFS 对应操作再增加 multipart 权限。

5.3 验证专用密钥​

已有 AWS CLI 时创建本地专用 profile，交互输入刚创建的密钥（配置只留在操作机）：

aws configure --profile langfuse-storage
aws --profile langfuse-storage --endpoint-url https://s3.example.com \
  s3api get-bucket-location --bucket langfuse-events
printf 'langfuse storage probe\n' > /tmp/langfuse-storage-probe.txt
aws --profile langfuse-storage --endpoint-url https://s3.example.com \
  s3api put-object --bucket langfuse-events --key events/probe.txt \
  --body /tmp/langfuse-storage-probe.txt
aws --profile langfuse-storage --endpoint-url https://s3.example.com \
  s3api get-object --bucket langfuse-events --key events/probe.txt \
  /tmp/langfuse-storage-probe.download.txt
cmp /tmp/langfuse-storage-probe.txt /tmp/langfuse-storage-probe.download.txt
aws --profile langfuse-storage --endpoint-url https://s3.example.com \
  s3 presign s3://langfuse-events/events/probe.txt --expires-in 60

在浏览器打开最后生成的短期签名 URL，应下载相同文本；URL 在有效期内代表访问权限，不转发到聊天或公开日志。再对 langfuse-media/media/probe.txt 做相同验收。没有 AWS CLI 时使用现有 S3 客户端完成同样的 put/get/presign/delete 检查，不必为了 Langfuse 另部署存储服务。

验证访问一个已存在的业务 bucket失败（例如 head-bucket），并用匿名请求读取测试对象确认拒绝。不要把 bucket 不存在的 404 当权限隔离证据。

验收后只删除本次 probe：

aws --profile langfuse-storage --endpoint-url https://s3.example.com \
  s3api delete-object --bucket langfuse-events --key events/probe.txt
rm /tmp/langfuse-storage-probe.txt /tmp/langfuse-storage-probe.download.txt

媒体/导出签名 URL 要让浏览器和 SDK 能访问；事件上传端点则供 Web/Worker 内网使用。配置模板分别提供 media 的外部和内部端点，均需指向 S3 API。反向代理必须保留 Host、路径、查询参数和签名相关头，禁止给签名 URL 加交互式登录或重定向；否则会出现 SignatureDoesNotMatch。浏览器直接上传媒体还需配置只允许 Langfuse origin 的 CORS，并验收预检；首期纯文本 trace 不依赖这一步。

6. 准备独立部署目录和参数​

本次部署目录是 /opt/langfuse。以下复制步骤用于新部署；已运行实例先备份并对比现有配置，保留已验证的 Redis、S3、地址、密钥和镜像，不直接覆盖。附件的服务器文件名是 compose.yaml 和 .env；本文模板使用 compose.yml、langfuse.env、migration.env，因此每条命令显式指定文件。

中间件地址和密码填写在 /opt/langfuse/langfuse.env 中。 从模板修改对应值，保留其余参数。compose.yml 已为 Web/Worker 配置 env_file: ./langfuse.env，启动时会将这些参数传入两个容器；不用再逐项拼接 docker run -e。Compose 环境变量传入方式。

7. 拉取、迁移和启动​

7.1 检查 Docker 和网络​

cd /opt/langfuse
docker info
docker compose version
docker compose run --help
docker network inspect chein-shared

本文迁移命令需要 docker compose run --env-from-file，先确认帮助中存在该选项；缺失则更新部署工具或使用下面的 docker run 等价命令。共享网络不存在时，先确认中间件网络名称；若全部通过外部 DNS/IP 连接，可创建此网络：

docker network create chein-shared

已有中间件在其他网络时改 LANGFUSE_DOCKER_NETWORK，不要重复启动它们。网络只负责可达；PG/RustFS 凭据按前文准备，Redis 使用现有密码。

7.2 检查参数并拉取镜像​

以下命令在部署服务器的 /opt/langfuse 目录执行。主流程只拉取 Web/Worker 镜像，地址来自 compose.yml 与 langfuse.env。已有中间件由其原部署维护。Compose 拉取命令。

cd /opt/langfuse
rg -n 'REPLACE_|example\.com' langfuse.env migration.env
docker compose --env-file langfuse.env -f compose.yml config --quiet
docker compose --env-file langfuse.env -f compose.yml config --images
docker compose --env-file langfuse.env -f compose.yml pull langfuse-web langfuse-worker
docker image inspect docker.langfuse.com/langfuse/langfuse:4.56.0 --format '{{json .RepoDigests}}'
docker image inspect docker.langfuse.com/langfuse/langfuse-worker:4.56.0 --format '{{json .RepoDigests}}'

rg 应无结果；不存在 rg 时用编辑器搜索占位符。inspect 中的镜像名要与配置中实际使用的镜像一致；沿用 Docker Hub :4 时相应修改，先记录现有 digest 再固定，不能把换仓库/标签当成原地修复。正式部署将两个 *_IMAGE 固定为 repository@sha256:...。目标服务器架构与离线镜像须一致，AMD64 传输见第 7.6 节。

7.3 核对 ClickHouse，串行执行一次官方迁移​

用已有 ClickHouse 管理连接核对版本、时区及应用用户授权：

SELECT version(), timezone();
SHOW GRANTS FOR langfuse;

把 langfuse 替换为实际用户。时区须为 UTC，用户权限限制在 Langfuse 所用数据库；如果现有 default 包含其他应用数据，应另选专用数据库并修改 CLICKHOUSE_DB。Langfuse ClickHouse 用户同时负责迁移和运行，需要 DDL、查询、写入、更新/删除及官方要求的 system 表读取权限，不能只授予 SELECT/INSERT。ClickHouse 配置与授权清单。

CLICKHOUSE_URL 使用 HTTP 8123（TLS 8443），CLICKHOUSE_MIGRATION_URL 使用 Native TCP 9000（TLS 9440）；单节点设置 CLICKHOUSE_CLUSTER_ENABLED=false，Native TLS 与 CLICKHOUSE_MIGRATION_SSL 保持一致。分别验证 Web/Worker 网络到两个端口的连接，宿主机 /ping 成功不证明容器到 Native TCP 可用。同机共享 Docker 网络优先使用 clickhouse 服务名；使用 LAN IP 时核对映射与防火墙。Tailscale 域名故障不能直接归因为 Docker 冲突。

所有中间件可达且授权正确后，串行执行一次迁移：

docker compose --env-file langfuse.env -f compose.yml run --rm --no-deps \
  --env-from-file migration.env langfuse-web node -e 'process.exit(0)'

使用固定 Web 镜像的官方 entrypoint 执行 PostgreSQL 和 ClickHouse 迁移，然后退出；不会增加常驻容器。migration.env 只覆盖这一次容器。成功退出前不要启动 Web/Worker；失败先排查地址、TLS、权限、磁盘和日志，不能设置忽略迁移来绕过错误。入口行为已按 4.56.0 entrypoint 核对。

旧版 Compose 缺少 --env-from-file 时可使用 Docker 原生命令（镜像/network 改为实际值，若已固定 digest 也使用同一 digest）：

docker run --rm --network chein-shared \
  --env-file langfuse.env --env-file migration.env \
  docker.langfuse.com/langfuse/langfuse:4.56.0 node -e 'process.exit(0)'

确认 PostgreSQL 和 ClickHouse 两套迁移都完成且容器退出码为 0。All migrations have been successfully applied 只代表 Prisma/PG 阶段，后续 ClickHouse 仍可能失败。迁移后按第 3.3 节检查表所有权和 runtime 权限；运行账户不得取得 CREATE，也不应成为 migrator 成员。本方案不授权 CREATEDB，不执行 migrate dev。

7.4 启动常驻服务并检查​

第 7.3 节迁移成功后执行。此命令只启动两个 Langfuse 服务，Web/Worker 的中间件配置由同目录的 langfuse.env 传入，已有 ClickHouse 继续由原部署维护。

docker compose --env-file langfuse.env -f compose.yml up -d langfuse-web langfuse-worker
docker compose --env-file langfuse.env -f compose.yml ps
docker compose --env-file langfuse.env -f compose.yml logs --tail 100 langfuse-web langfuse-worker
curl -fsS 'http://127.0.0.1:3000/api/public/health?failIfDatabaseUnavailable=true'
curl -fsS http://127.0.0.1:3000/api/public/ready
curl -fsS http://127.0.0.1:3030/api/health

常驻容器自动迁移已关闭，必须保留“先迁移再启动”的部署步骤；此选择用于不向常驻服务暴露 PG owner 密码。不要只重启容器就认为升级完成。

Web 默认 health 主要检查进程，ready 也不代表完整 ingestion 链路；以上检查通过后，还必须发送一条真实合成 trace，确认 Worker 消费并落到 ClickHouse。官方健康端点。

7.6 Mac 到 AMD64 服务器的离线镜像传输​

下面使用仓库固定版本；维护现有实例时替换为已记录的镜像版本/digest，Web/Worker 保持配对。归档放在项目外，先确认本机有足够空间：

docker pull --platform linux/amd64 docker.langfuse.com/langfuse/langfuse:4.56.0

scp langfuse-amd64.tar YOUR_DEPLOY_USER@YOUR_DEPLOY_HOST:/tmp/

sha256sum /tmp/langfuse-amd64.tar
docker load -i /tmp/langfuse-amd64.tar

离线服务器将第 7.2 节的 pull 改为上述 load，确认导入标签与 Compose 一致，再执行迁移和启动；不要用 :4 的归档冒充 :4.56.0。save --platform 需要 Docker API ≥1.48，先用 docker save --help 确认支持。Docker 导出平台说明。

服务器缺少 psql 时可同样离线传输与服务端主版本一致的客户端镜像。本次复盘记录 PG 服务端 18.3、客户端 17.11，后续示例使用 18 系列；不据此断言旧客户端所有操作兼容：

客户端示例地址、网络和 TLS 设置按真实环境填写。只有本机已经拉取过对应镜像时才导出；镜像损坏与未下载平台的导出错误须区分，见第 13 节。

8. Langfuse 登录账户、项目与 API Key​

8.1 首次创建管理员​

  1. 通过 SSH 隧道访问 http://localhost:3000，或访问受限的 HTTPS 入口。
  2. 用你自己的邮箱注册独立 Langfuse 账户，设置强密码。自托管实例的账户独立于 Langfuse Cloud 和 Chein，不需要先注册云账户。

8.2 团队账户、邮件与注册开关​

使用自己的真实发件地址和 SMTP 服务；端口、TLS/STARTTLS 按邮件提供商要求，不必部署新邮件服务器。重建 Web/Worker 并实际验证邀请与密码重置邮件送达。SMTP 配置。

8.3 切换最终 HTTPS 地址​

初始化完成后，将运行参数设回最终 URL：

NEXTAUTH_URL=https://langfuse.example.com
LANGFUSE_CSP_ENFORCE_HTTPS=true
AUTH_DISABLE_SIGNUP=true

在已有 Nginx 的 TLS vhost 中配置下面的 location（证书/DNS 使用现有运维方式）。Nginx 在宿主机时上游用 127.0.0.1:3000；Nginx 在同一 Docker 网络时改为 langfuse-web:3000。

使用 Higress 或其他容器反代时同样核对网络：代理容器不能通过自己的 127.0.0.1:3000 访问 Web。让代理与 Web 共享网络并使用服务名，或使用已限制来源的宿主机地址；入口 URL 与 NEXTAUTH_URL 保持一致。

location / {
    proxy_pass http://127.0.0.1:3000;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_read_timeout 120s;
    client_max_body_size 20m;
}

20m 是本方案纯文本冒烟的起步限制，未来大量事件/媒体按实际请求大小调整。HTTPS 代理不能只代理首页，必须放行 SDK 使用的 /api/public/otel/v1/traces 和认证 API；初期建议整体仅在 VPN/内网可达。

nginx -t
# 在确认检查成功后，按现有部署方式 reload Nginx。
docker compose --env-file langfuse.env -f compose.yml up -d --force-recreate langfuse-web langfuse-worker

随后使用最终域名重新登录，并从 Agent 所在环境确认可达。SDK 的 URL 使用根地址，不在 LANGFUSE_BASE_URL 后面加 /api 或 /otel/v1/traces。

11. 备份、保留和升级​

  • 备份：备份 langfuse PG 数据库、Langfuse 所用 ClickHouse 数据库、专用 bucket 和部署私有配置。将 ENCRYPTION_KEY/SALT 保存到受控密钥备份。定期做恢复演练，只有 PG 备份不能恢复 trace 数据；共享 ClickHouse 的备份/恢复不能覆盖其他应用数据库。
  • ClickHouse：使用其受支持的备份机制或停止写入后的存储快照；不要把运行中 volume 的普通 tar 当作一致备份。此方案不提供热备脚本。
  • Redis：监控队列积压、内存和持久化；共享实例禁止为 Langfuse 排障执行 FLUSHDB/FLUSHALL。备份/回滚也不得覆盖其他应用队列。
  • 保留期：上线前明确要保留多少天及清理责任人。未配置清理不能假定自动保留 30 天；Langfuse 原生保留期功能须核对当前部署版本/许可。RustFS lifecycle 与 ClickHouse 保留是不同层，清 bucket 不会自动清观测表。
  • 升级：备份 → 停止 Langfuse Web/Worker（不停止现有业务中间件）→ 更新成对镜像及 digest → 核对 release/migration 要求 → 串行运行第 7.3 节迁移 → 启动 → 再跑合成 trace。迁移文件只临时提供给一次性容器。
  • 回滚：数据库迁移后不能保证换回旧镜像即可运行；按升级说明还原对应 PG/ClickHouse 备份，并核对 S3/队列状态。禁止 docker compose down -v 当回滚；三服务备选模板下该命令会删除 ClickHouse 持久卷，外置实例也不能随应用重建而重置。
  • 账户轮换：逐类轮换 PG/RustFS/项目 Key，重建相关服务并冒烟。Redis 共享密码轮换必须协调全部使用方。撤销旧 Key 后确认旧凭据被拒绝；不要随意轮换用于解密的 ENCRYPTION_KEY。

13.1 permission denied for schema public​

先检查真正执行迁移的容器是否收到 migrator 的 DIRECT_URL，再检查 public 的 USAGE/CREATE 和已有表 owner。只在数据库里授权、没有把迁移 URL 传进容器，仍可能报错；授予 schema CREATE 也不等于获得已有表的 ALTER 权限。按第 3、6、7.3 节修正，不把 runtime 提升为 owner 或超级用户。

检查配置时只输出变量存在性；完整 env/Compose 输出可能包含凭据：

docker compose --env-file langfuse.env -f compose.yml exec -T langfuse-web node -e '
for (const key of ["DATABASE_URL", "DIRECT_URL", "NEXTAUTH_SECRET", "SALT", "ENCRYPTION_KEY"]) {
  console.log(key + "=" + (process.env[key] ? "<configured>" : "<missing>"));
}
'

变量存在不证明身份正确；由操作人在私有配置中核对 URL 的角色、数据库与 TLS，迁移覆盖项只检查一次性容器。

13.2 Prisma P3009 与 20230720162550_tokens​

复盘记录该条迁移失败。用户在当时的 observations 表中核对了三个 token 列的类型、可空性和默认值，备份失败记录后手动设置 finished_at；后续 PG 迁移才继续完成。这是一次特定恢复经历，不是可直接复用的数据库修复脚本。

在 DataGrip 的 langfuse 管理连接中先查失败记录及对应列：

SELECT migration_name, started_at, finished_at, rolled_back_at, logs
FROM public._prisma_migrations
WHERE finished_at IS NULL AND rolled_back_at IS NULL
ORDER BY started_at;

SELECT column_name, data_type, is_nullable, column_default
FROM information_schema.columns
WHERE table_schema = 'public' AND table_name = 'observations'
  AND column_name IN ('completion_tokens', 'prompt_tokens', 'total_tokens');

第二条只用于该迁移阶段的结构核对；表已在后续版本变化时不套用历史结果。恢复前备份数据库，逐项对照失败迁移所属镜像版本的 SQL，判断是否部分执行；不能仅凭三个列存在就跳过整个迁移，也不能删除 _prisma_migrations、批量更新 finished_at 或重建已有生产库。

优先用匹配版本 Prisma 的 migrate resolve：未完成的变更先补齐再标记 --applied，需要重试时先处理已执行部分，再标记 --rolled-back。两者都不会替你完成或撤销业务 DDL，恢复后仍须重新执行第 7.3 节并检查 PG 与 ClickHouse。Prisma 官方恢复流程。

附件称生产容器没有 npm/pnpm、无法通过它们调用 Prisma。这不能推出镜像没有独立 prisma：仓库固定的 4.56.0 Dockerfile 安装独立 CLI，entrypoint 也直接调用它。先在实际镜像中检查支持的命令，覆盖 entrypoint 以避免检查时执行迁移：

docker compose --env-file langfuse.env -f compose.yml run --rm --no-deps \
  --entrypoint sh langfuse-web -c 'command -v prisma && prisma migrate resolve --help'

若实际镜像缺少该工具，准备与其 Prisma/schema/migrations 一致的工具环境。执行恢复时显式传入 migrator 凭据；不要在常驻容器安装最新版 npm/pnpm 或使用仓库 Agent 的依赖代替 Langfuse 迁移工具。

13.3 PG 完成，ClickHouse 仍报 driver: bad connection​

All migrations have been successfully applied 后出现 SHOW TABLES ... schema_migrations 失败，说明 PG 阶段成功而 ClickHouse 阶段失败。分别检查 Native TCP 地址、9000/9440 可达性、TLS 开关、DNS、单节点开关与 DDL 权限；8123 /ping 成功只证明 HTTP 端点响应。socket hang up、ECONNRESET 本身不足以证明 Tailscale 与 Docker 冲突，同机优先改用共享网络服务名，修复后重跑第 7.3 节。

13.4 登录页报 permission denied for table users（42501）​

迁移用户创建了表，runtime 却没有现有表的 DML 权限。按第 3.2、3.3 节对全部 Langfuse 表和序列检查、补授权，并设置 migrator 的未来默认权限。只授权 users 会让其他页面或任务继续失败；不要给 runtime 超级用户权限。

13.5 Invalid credentials​

核对账户是否存在、登录方式、注册/SSO 开关、NEXTAUTH_URL 与稳定的会话密钥，并检查 Web 中实际错误。复盘只确认最终登录成功，没有足够证据给出该提示的唯一根因；不通过 SQL 直接修改密码哈希。

13.6 AMD64 拉取成功提示，但镜像不可见或无法导出​

本会话已在 Mac 的 OrbStack 复现：docker pull 显示成功，inspect 返回 layer does not exist，镜像列表为空。普通删除和重启无效；经用户明确授权，仅重置 OrbStack 内部数据后重拉 linux/amd64，镜像读取、隔离 Node 运行和指定平台的导出检查通过。该本地结果不代表服务器镜像或服务验收通过。

另一个导出错误是 content digest ... not found：本次指定 docker save --platform linux/amd64 后通过，与已确认的镜像层损坏不能混为一谈。先检查目标平台是否存在，再按第 7.6 节导出；不要只看 pull 的成功提示。

OrbStack 重置会删除其 Docker/虚拟机数据，必须先盘点并备份、获得明确授权；本文不将全量重置作为普通拉取失败的默认处理，也不清理其他应用数据。附件关于 postgres:17 导出问题仅保留为其用户记录，不能把该次处理归因到本会话的 Langfuse 镜像故障。
