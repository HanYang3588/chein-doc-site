Chein Agent 可观测性架构审计（2026-10-20）

本报告是当前工作区与目标 Langfuse 的审计快照，不替代 Agent 架构基线、观测交付说明或隐私契约。工作区包含此前未提交修改，结论对应审计时的文件内容，行号会随后续开发变化。

后续状态：用户于审计后授权优化，2026-10-21 的代码修改与本地验证见 审计后优化交付。下文保留审计当时的结果与计划，不表示这些缺口至今全部未处理，也不代表优化已经部署。

本次仅新增报告并更新文档导航。没有修改业务代码、依赖、配置或部署文件，没有安装依赖、重启服务、触发 Agent 对话、提交评分或运行付费评估。对 Nacos 和 Langfuse 只做读取；不在报告中保存凭据、私有服务地址、业务正文、原始用户标识或真实 Trace ID。

1. 当前架构结论​

需要先纠正任务中的前提：Agent 已经使用 Langfuse Python SDK，并且 SDK 底层也是 OpenTelemetry。 backend/.venv 没有 Langfuse，不能代表独立 Agent 的依赖环境。

核心问题审计结论证据边界
Chein 使用什么实现 Trace？Agent：Langfuse SDK 4.17.0、官方 LangChain Callback 的脱敏子类、私有 OTel Provider 和自定义 OTLP Exporter；Backend：共享包中的原生 OTel代码、已安装依赖、运行进程和存量 Observation 均有证据
是否已经使用 OTel？是。两端均使用 OTel SDK 1.45.1；Agent 的 Langfuse SDK复用传入的 Provider 和 Exporter不是相互排斥的两种实现
是否使用 Langfuse SDK？Agent 使用；Backend 不使用，符合现有架构边界agent/pyproject.toml:25 与实际 Agent 虚拟环境一致
上报协议是什么？OTLP/HTTP Protobuf，目标为配置 origin 加 /api/public/otel/v1/traces，Basic 项目密钥认证，携带 ingestion version 4两端代码一致；目标服务已有对应存量数据
Langfuse 承担什么角色？Trace/Observation 接收、查询、可视化、用量展示及评分/评估平台；不是权限、业务状态或 Prompt 正文的权威源Prompt 仍由既有 Nacos 链路管理
是否必须部署 Collector？当前不需要；两端已经直接上报并形成完整样本链路Collector 不能解决空评估正文、价格映射或缺少业务 Span
是否存在重复追踪？存在多类观测渠道，但未发现同一次 Agent 执行被两套 Langfuse Callback/Exporter重复发送的证据抽查完整 Trace 无重复 Observation ID；不能证明所有执行分支都没有语义重叠

建议采用方案 C：保留现有混合方案，补齐有实际价值的语义、诊断和评估条件；不再引入第二个 Langfuse 客户端或做技术名称上的迁移。

2. 证据等级与审计范围​

本报告区分四类事实：

  • 代码已实现：静态调用链存在，不等于目标环境成功执行过。
  • 配置已声明：读取当前 Nacos 内容或仓库模板；不能自动证明既有进程已经重载。
  • 运行时已验证：读取进程、实际虚拟环境依赖或目标 Langfuse 已有记录。
  • 待验证：需要界面检查、合成执行、故障注入或跨租户测试，本次没有越过只读范围执行。

检查范围包括 agent/、backend/、observability/、根启动脚本、Compose/Dockerfile、Nacos 模板及相关专题文档；另读取当前 Nacos 的非敏感配置结论、运行进程和目标 Langfuse 的健康/Observation 接口。读取 API 响应后只保留结构与汇总，不在文档落地业务内容。

历史 Langfuse 审计属于接入前快照，不能据此判断当前 SDK 缺失。已有测试文件仅用于理解契约，本次没有重新执行业务测试，也不引用旧测试数量作为本次验证结果。

6.1 Trace / Span / Parent 传播​

  1. BFF 创建全新请求根，拒绝把浏览器自带 traceparent 直接当作可信 parent；内部代理附带服务签发身份和新 traceparent。
  2. Agent 在 run_agent_stream:887 验证 Run/Thread 的 delegated context 后，才将 traceparent 传到 execution_scope。后者沿用 Trace ID，并指定正确 Parent Span ID。
  3. 官方 Callback 显式以 agent.execution 为 parent；手工阶段复用当前 OTel context。user.id、session.id 使用带 tenant/owner/thread 的 HMAC 引用，同一会话多轮具有稳定 Session 关联；每次执行仍可有不同 Trace。
  4. Agent → Backend MCP/Knowledge 使用 trace_headers；Backend 在 JWT/权限校验后调用 trusted_parent:109。只传播 traceparent，不传播任意 baggage/tracestate。
  5. 当前抽样 12 个节点父子关系完整。Memory 定时 HTTP tick、部分目录/来源授权接口及外部 RAGFlow 内部调用不在该保证范围内。
  6. Backend sampler 是 ParentBased，Agent 是 TraceIdRatioBased；当前均为 1.0，不构成已观察到的断链。降低采样率后应验证 remote parent sampled 标志的一致性，否则可能产生父子采样分歧。

不同 Run/lease epoch 有独立 execution 引用，恢复流程的映射不能只用 Thread ID 代替。PG 中的消息映射与当前授权重验才是查询权限依据，Trace ID 本身不是凭证。

Prompt 关联无 Langfuse Prompt 对象/版本关联；Nacos 为事实源有意保持现有所有权；可考虑只带非敏感版本指纹，不迁移正文管理

Langfuse 接受原生 OTLP，也识别 Langfuse 专有属性；官方 OTel 文档说明两者可互通，专有属性优先。现有过滤策略会删除未授权字段，不能只在业务层添加字段就假定最终可见。

7.2 为什么配置了 redacted-content，Evaluator 仍可能没有可评估内容​

Runtime.__init__:368 将全局 AGENT_MEMORY_ENABLED 作为 memory_private；:438 和 execution_scope:743 都要求 redacted-content-v1 AND NOT memory_private 才收集选定问答。该判断不是逐用户的个人记忆 opt-in。

当前 Nacos 同时开启 Memory 与 redacted-content，因此这条路径实际阻止问答导出。最近三个 agent.execution Observation 的 input/output 均为空，与代码一致。根 metadata 中仍写配置名 redacted-content-v1，缺少明确的“有效正文策略/被抑制原因”，容易误导运维。

这首先是隐私保护契约，不应为了让 Evaluator 工作直接删除门禁。当前 可读链路设计和长期记忆边界需要共同评审；优先使用获准合成数据和独立评测项目。

还需检查 Evaluator 的实际目标：官方 LLM-as-a-Judge 文档指出，Observation 级评估只读取匹配 Observation 的变量，不自动拼接同 Trace 的兄弟/子节点。若评估整体问答，应核对 agent.execution 的 app-root 标记、规则过滤和变量来源；不能因它有 Backend 物理 parent 就认定不是逻辑应用根。

Langfuse v4 使用 Observation 数据模型，旧 Trace 顶层 input/output 空值本身不足以判断内容丢失；官方说明也要求查看 Observation。本次已经直接查询 Observation 的 io 字段，证据比查看旧 UI 字段更强。

7.3 Scores、Datasets 与 Evaluators​

  • telemetry_api.sync_feedback:189 已通过自定义 HTTP 客户端调用 POST /api/public/scores，以稳定 score_id 与 PG revision 同步，包含 trace/observation 关联，不外发纠正文本。此能力已实现，本次不做写入验收。
  • observation_summary:93 已使用 v2 Observation 查询，并限制为当前授权执行子树；不以任意 Trace ID 直通查询整个共享项目。
  • quality.publish_replay:274 已有受控 Dataset 创建、Dataset Items 与 SDK run_experiment，校验独立评测项目、合成/批准数据与请求预算。不是“没有 SDK 所以没有 Dataset”。本次没有调用该发布流程。
  • Evaluator 的 UI 定义不等于有效的触发规则。本次两个只读管理 API 返回 404，无法确认这台 4.56.0 的规则 API 可用性、UI 中所选项目、目标字段或已有评分结果，不能用 SDK 支持该方法来证明服务器支持它。
  • background_sync:252 是有限时单次后台尝试；失败保留 PG pending，并有显式 replay 入口。未发现一个持续自动重试所有 pending 反馈的独立守护任务，不能宣称最终一定自动补齐。

7.4 SDK / Server 兼容性​

当前 Server 4.56.0 + Python SDK 4.17.0 + OTel 1.45.1 已通过实际 Observation 读回证明核心 tracing 可用。协议头也满足 v4 实时接收要求；没有测量实际端到端可见延迟。
