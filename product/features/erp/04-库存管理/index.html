库存：余额、流水、出入库、调拨、盘点

状态：操作与事实说明（以 application/inventory_posting.py、stock_routes.py 为准）。

适用范围：所有会改变库存的业务（采购入库/退货、销售出库/退货、其他出入库、调拨、盘点）。

1. 两个事实源​

表性质说明
erp.stock_balance当前态，仅经 InventoryPostingService 写入每个 (tenant_id, product_id, warehouse_id) 一行，quantity 是当前结存，version 每次变动 +1；业务代码不得直接改这张表
erp.stock_ledger历史，只追加每条 delta_quantity 与 balance_after；不允许 UPDATE/DELETE

核心不变式：

  1. stock_balance.quantity = SUM(stock_ledger.delta_quantity)（按商品 + 仓库）。
  2. stock_balance.quantity >= 0（数据库 CHECK + 应用校验，任何会导致负库存的单据整体回滚）。
  3. stock_ledger.source_version 记录的是该单据操作完成后的版本号（即 document.version + 1）。
  4. 反向操作不改写原分录，而是新增一条 reversal_of_id = 原分录 id 的反向分录。

2. 唯一的写入口：InventoryPostingService​

InventoryPostingService.post() 是 ERP 里唯一允许修改 stock_balance 的地方， 所有单据审批都走它。执行顺序：

  1. 校验效果集合非空（empty_document）、没有 0 数量分录（zero_effect）。
  2. 校验商品与仓库存在且启用（product_unavailable / warehouse_unavailable）， （反向操作时跳过此检查，允许引用已停用的商品/仓库，避免历史单据无法冲销）。
  3. 按 (product_id, warehouse_id) 的字符串序排序后逐个加锁： 先 INSERT ... ON CONFLICT DO NOTHING 保证余额行存在（初始 quantity = 0）， 再 SELECT ... FOR UPDATE 取行锁——固定加锁顺序用于避免并发死锁。
  4. 如果传入了 expected_quantities（盘点场景），先比对当前余额与快照， 不一致直接报 stock_balance 快照过期（reason snapshot_stale）。
  5. 逐条累加余额，出现负数即抛 insufficient_stock。
  6. 每条分录写入 stock_ledger，并往 Outbox 投递 erp.stock.changed 事件 （aggregate_id 形如 <product_id>:<warehouse_id>，aggregate_sequence = balance.version）。

冲突原因码（对应 InventoryConflictError.reason，也是 erp_stock_conflicts_total{reason=...} 指标标签）：

empty_document、zero_effect、product_unavailable、warehouse_unavailable、 snapshot_stale、insufficient_stock。

3. 单据类型与库存分录对照​

业务单据表ledger_type（正向）数量方向反向 ledger_type
采购入库purchase_inpurchase_in+purchase_in_reversal
采购退货purchase_returnpurchase_return-purchase_return_reversal

其他出库stock_outother_out-other_out_reversal

stock_ledger.source_document_type 使用下划线形式：purchase_in、sale_out、 stock_in、stock_out、stock_move、stock_check 等。

4. 调拨与盘点​

调拨（KCDB）：一条明细同时在转出仓写 move_out（负）、转入仓写 move_in（正）， 两者在同一事务内完成；明细的 from_warehouse_id 与 to_warehouse_id 必须不同（数据库 CHECK）。 审批时必须对两个仓库都有权限。

盘点（KCPD）：

  • 明细列 snapshot_quantity（盘点时的账面数）、actual_quantity（实盘数）、 difference_quantity = actual - snapshot（数据库 CHECK 强制该等式）。
  • 审批时以 snapshot_quantity 作为 expected_quantities 传入， 要求当前余额仍等于快照；若盘点期间发生了别的出入库，直接报 Stock snapshot is stale（reason snapshot_stale），需要重建盘点单。
  • 差异过账：> 0 记 check_gain，< 0 记 check_loss，= 0 的行不产生分录。
  • 反向：写 check_*_reversal 分录，单据回到 draft、version + 1。

6. 排查​

Q：库存余额和流水对不上

SELECT b.product_id, b.warehouse_id, b.quantity AS balance,
       COALESCE(l.total, 0) AS ledger_total
FROM erp.stock_balance b
LEFT JOIN (
  SELECT product_id, warehouse_id, SUM(delta_quantity) AS total
  FROM erp.stock_ledger WHERE tenant_id = '<tenant>'
  GROUP BY product_id, warehouse_id
) l ON l.product_id = b.product_id AND l.warehouse_id = b.warehouse_id
WHERE b.tenant_id = '<tenant>' AND b.quantity <> COALESCE(l.total, 0);

返回结果不为空时，先跑一次对账（见 06-对账与一致性.md）拿差异样本， 再按 stock_ledger 的 source_document_type/source_document_id 回溯是哪个单据引入的偏差。

Q：某次库存变动是谁造成的

SELECT l.occurred_at, l.ledger_type, l.delta_quantity, l.balance_after,
       l.source_document_type, l.source_document_no, l.source_version,
       l.reversal_of_id, l.operator_id
FROM erp.stock_ledger l
WHERE l.tenant_id = '<tenant>' AND l.product_id = '<product>'
  AND l.warehouse_id = '<warehouse>'
  AND l.occurred_at >= '<from>' AND l.occurred_at < '<to>'
ORDER BY l.occurred_at;

reversal_of_id IS NOT NULL 的行是冲销分录，必须和它指向的原分录成对阅读。

Q：为什么盘点审批报 "Stock snapshot is stale"

盘点明细的 snapshot_quantity 是建单（或上次刷新）时的账面数，审批时会与当前余额严格比对。 常见原因：盘点单停留在 draft 期间又发生了入库/出库/调拨。处理方式：刷新盘点单的数量后重新提交， 而不是直接改 stock_balance。

Q：为什么库存不会变负，但业务上确实少发了

负库存被应用层拒绝（insufficient_stock），所以不会出现负余额； 若业务上出现"发了货但库存没减"，检查对应出库单是否真的审批过（status = 'approved'）， 以及是否被反向（document_action_log.action = 'reversed'）。

Q：为什么 stock_ledger 改不了

这是设计约束：ErpTenantUnitOfWork 在 flush 阶段禁止修改或删除 stock_ledger 与 document_action_log（报 ERP append-only record is immutable）。修正历史只能通过新的反向/ 调整单据。
