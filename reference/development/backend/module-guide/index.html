新增业务模块指南

前端接入说明更新：2026-09-20；当前 React 实现和目标模块结构分别标注，后端模块契约不变。

业务模块的边界、模块契约、产品发行版和部署组合见模块化产品架构规划，具体实施顺序和验收门禁见模块化架构实施基线，公开接口与依赖规则见 ADR-0009。本指南描述目标模块结构；现有集中式代码可以渐进迁移，但新业务模块不得继续扩大 app.models、app.api.routes 和集中式菜单种子。

以 Items 为范例，一个完整模块应包含：

  • SQLModel 数据模型。
  • Alembic 迁移。
  • CRUD/API 路由。
  • 权限码和初始化菜单。
  • 前端 API 封装。
  • 前端列表、查询、新增、编辑、删除页面。
  • 测试和文档。

后端​

目标目录如下：

backend/app/modules/<module_code>/
  module.py
  public_api/
    queries.py
    commands.py
    dto.py
    events.py
  domain/
  application/
    ports.py
    services/
  infrastructure/
    models.py
    repositories.py
  routes/
  permissions.py
  menus.py
  migrations/
  1. 在 module.py 声明模块版本、必选依赖、可选能力、Router、权限、菜单、迁移、事件和生命周期组件。外部连接池可通过 LifecycleHooks.on_shutdown 注册关闭函数，由 API lifespan 在停止 MCP/后台工作后释放；不能把关闭行为绑定到每次请求。
  2. ORM 模型、Repository 和外部系统适配器放在模块自己的 infrastructure，不能加入全局 app.models。
  3. FastAPI Router 放在模块自己的 routes，并通过平台稳定 Web 集成面使用 require_module_access("<module>", "<permission>")。
  4. 跨模块需要调用的查询、命令、DTO 和事件放入 public_api；纯模块内部接口不要放入公开目录。
  5. 对平台用户、租户、组织和权限的读取依赖平台公开端口，不直接查询平台表。
  6. 对其他业务模块的必选依赖只能导入其 public_api，并在模块声明中登记。
  7. 对审批等可选能力只依赖稳定能力契约，由组合根选择 Provider；禁止直接导入可选模块实现。
  8. 增加单元测试、公开契约测试、接口测试和 edition 独立启动测试。

模块向 Agent 提供只读业务工具时，在 ModuleDefinition.agent_tools 声明 AgentToolSpec。工具名以 _v1 等主版本结尾，权限使用本模块前缀；处理函数复用当前业务查询，逐次重验授权并进入模块 UoW。后端组合根只发布当前 Edition 的工具，BFF 自动推导可委托权限。Schema 变更发布新的 Nacos 服务版本，接入步骤见工具管理实施设计。

后续只读接口优先复用同一 /mcp 服务和 Agent 的 AGENT_MCP_SERVERS，不为每个业务接口增加 Agent URL。参考 app/modules/analytics/agent_tools.py；跨可选模块仍经 capability。普通工具直接由已有 MCP loader 装配；像分析这类需要快照、精确数值和有界模型摘要的工具，在 Agent 保留处理层，底层结果工具不重复交给模型。写接口仍需单独的审批、幂等和审计设计。

在模块注册器和菜单声明完全落地前，允许在组合根增加一次显式注册，但业务实现不能放回中央文件。该兼容步骤必须带有迁移 TODO，不能成为长期接入方式。

公开接口设计​

公开接口应围绕调用方用例设计，例如批量解析用户摘要、发起审批或检查业务引用，不提供跨模块通用 ORM CRUD。

  • 输入输出只使用 Pydantic DTO、不可变 dataclass、枚举和标准类型。
  • 不公开 ORM 实体、数据库 Session、FastAPI 请求对象、内部异常和第三方 SDK 对象。
  • 查询接口不得允许调用方拼接提供方数据库过滤条件。
  • 命令接口定义幂等键、超时和稳定错误码。
  • 破坏性契约变更创建新主版本；旧版本按发布策略保留迁移周期。
  • 公开接口测试使用替身实现时，不应要求初始化提供方 Router 或数据库表。

跨模块事件​

改变其他模块业务状态的事件必须通过事务 Outbox 发布，事件 Schema 放在发布方 public_api.events。事件至少包含 event_id、event_type、event_version、tenant_id、aggregate_id、occurred_at 和追踪标识。

消费者必须：

  • 只依赖事件 DTO，不依赖发布方 Outbox ORM 模型。
  • 按 event_id 幂等处理。
  • 接受同一主版本内新增可选字段。
  • 对失败执行重试、死信和可观测处理。

前端​

当前交付应用为 frontend/apps/web-pro。新业务模块的目标目录如下，不能把它误读为 已经生成的现成模板：

frontend/apps/web-pro/src/modules/<module_code>/
  api/
    generated/
    index.ts
  pages/             # React / TSX
  components/
  hooks/
  locales/
  1. 当前唯一页面映射入口是 src/runtime/page-registry.ts 的受控 pageMap，Items/ERP/Knowledge/Analytics 按生成的 Manifest 条件注册。新模块接入复用该入口；目标静态模块契约/注册生成器尚未在 React 落地，不另建第二套注册机制，也不要引用不存在的 module.ts 当作已实现 API。
  2. 新增页面、私有组件、Hooks 和 API 包装保存在模块内，不继续加入中央业务 pages / api。
  3. 只依赖本模块生成客户端和 Platform 公共客户端；React Platform 输出在 src/services/generated/platform，禁止导入其他可选业务模块客户端。
  4. 后端菜单 component 必须有受控 React 映射；既有 .vue 字符串是兼容 key，不是文件加载路径。 未启用模块不注册运行入口，Base 产物还需检查是否打入可选模块代码。
  5. 页面和按钮复用 runtime/permissions.ts 的 can / hasPermission 或 Umi access；不使用 Vue 的 v-access:code / Vben auth。后端 require_module_access 才是安全边界。
  6. 使用根目录 pnpm generate:api -- --edition <edition> 生成契约，再运行 React 类型检查、 Vitest 和受影响 Edition 构建；不要使用模板 Umi openapi 命令代替仓库生成器。

现有 Items、ERP、Agent 页面仍在集中式 src/pages；Knowledge 和 Analytics 页面已在各自模块目录。前者迁移到模块目录属于后续实现任务。 当前源码与目标目录的区别见前端架构。

业务脚手架与 API 生成不要混淆​

历史设计中的数据库表转 FastAPI/Vben ZIP 生成器不是当前可用入口。当前 backend/app/platform/bootstrap_navigation.py 的 remove_obsolete_menus 已将 /system/codegen 与 system:codegen: 列为清理对象，源码未找到对应业务生成器实现。 不要再指导用户进入该菜单下载 Vue 页面，更不能把它说成 React 模块生成器。

当前可用的 pnpm generate:api 只生成 OpenAPI 类型/客户端与 Manifest，不生成业务页面、 业务模型、迁移或 Router。新增模块复用仓库实现模式，按本指南显式补齐模块目录、权限、 租户、迁移与测试。将来若重新引入脚手架，应直接输出 React 模块结构，单独完成设计和验收。

发布前检查​

新增模块进入发布前，至少确认：

  • 后端路由使用 require_module_access("<module>", "<permission>")。
  • 模块通过自己的定义注册 Router、菜单、权限、迁移和生命周期组件。
  • 模块没有导入其他模块的内部包、ORM 模型、Service 或 Repository。
  • public_api 没有反向导入 domain、application、infrastructure 或 routes。
  • Manifest 依赖声明与静态导入结果一致。
  • 可选 Provider 缺失时，模块独立启动和降级测试通过。
  • 跨模块事件具有版本化 Schema、幂等消费和重试测试。
  • 前端页面没有绕过权限展示危险操作入口。
  • 对应模块 OpenAPI 客户端已生成，组合契约没有命名冲突。
  • 受影响后端测试、pnpm frontend:typecheck、pnpm frontend:pro:test、pnpm frontend:build 通过。
  • 受影响 Edition 构建、React 客户端 drift 与真实浏览器流程分别有证据。
