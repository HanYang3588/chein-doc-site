Neo4j / APOC / n10s 代码审计

范围：当前未提交工作区；用户本轮要求先完成代码审计。本轮不修改实现、不操作远端图库，仅新增本报告及导航。

后续已使用用户配置的正常连接完成真实实例验证。下文保留审计当时的配置与证据；后续实测本身不代表 R1–R5 已修复。随后代码修复与专项证据见双工作区交付，下文问题清单保留审计时事实。

结论与证据边界​

现有实现是 PostgreSQL 发布模型的 Neo4j 语义投影读取器，还不是 RDF/OWL 本体引擎。Neo4j Provider 确实执行官方 Driver 与固定 Cypher，不是纯内存假实现；但读取的仍是 Chein Snapshot/Element JSON，普通图边、外部 n10s RDF、SHACL 和推理结果都没有进入 Agent 查询链路。APOC 无生产调用；当前有界投影和 ERP 查询不需要为了插件使用率引入 APOC。

上轮设计明确限定了投影和只读能力，见 双 Provider 设计。本轮附件要求的标准本体语义、出库业务判断和真实模型对照，是尚未实现/验收的目标，不能把这类缺口写成已通过，也不能绕过现有发布与 ACL 直接信任外部 RDF。

用户报告 Ubuntu 上 Neo4j/APOC 2026.10.1 和 n10s 已运行、RDF 导入已验证。本轮没有远端连接，未独立核验该报告。当前工作区 bootstrap 的设置仅输出是否配置：provider=auto、neo4j_enabled=false、URI/用户名/密码均未配置；因此本次配置启动的查询会选 Legacy。这不证明另一台机器上的已运行 Backend 使用相同配置。用户已明确选择先完成代码审计。

问题清单​

R1 — P1：最终权限复验漏掉指标和关系端点​

位置：runtime.py，_finish 113–116 行；指标入口为 metric 404–427 行。

_finish 已重新获取当前授权目录，却只检查 request.object、result.objects 和 result.nodes。MetricQuery.object 默认可以为空，指标结果通过 rows 返回，不命中这些检查；describe(object="Product") 的关联关系也不检查两端是否仍在新目录内。

触发条件：ERP 已执行授权读取，之后源资源权限被撤销，最终目录复验已看到撤权，而 ontology:query 权限及发布版本仍有效。代码探针模拟这个时序，结果为：

revoked relation endpoints still returned: ['line_product_v1']
metric returned after catalog revocation: True

这是最终复验的覆盖缺口，不是“所有指标都未授权”或“已确认跨租户泄漏”。数据所有者前面的授权仍存在；缺陷在于最终已知撤权未失败关闭。

建议：在最终响应前解析指标绑定对象并检查当前资源/指标目录；检查所有返回关系的两端和 binding。拒绝整个失效结果，不能仅删除对象后保留指标或关系。补充在读取后撤销权限的负向测试。本轮未修复。

R2 — P1（相对于新目标）：n10s RDF/OWL 与业务 Provider 仍完全分离​

位置：neo4j.py，READ 20–34 行、_load 166–197 行、health 249–279 行；dto.py 的 OntologySchema。

实际读取只有 CheinOntologySnapshot -[:CHEIN_CONTAINS]-> CheinOntologyElement，通过 payload 重建原 JSON，并强制匹配 PostgreSQL 发布摘要。CHEIN_RELATES_TO 在投影时创建，但生产读取和实例遍历均不使用它。外部导入的 Resource/Class/Property/URI 没有到已发布 Chein 对象的适配；健康检查只是枚举名称，未执行 RDF 导入、GraphConfig 读取、SHACL 或基础推理。

所以独立在服务器执行 n10s 导入，既不会使该本体被 Agent 搜到，也不会影响现有发布校验。缺少 Chein 投影时会明确报 missing；不能放宽摘要校验或回退策略来掩盖语义映射缺失。

建议：先定义受审核的 URI/namespace/Class/Property 到现有 DSL 和数据 binding 的映射、支持的公理子集及不支持语义的拒绝/保留策略，再接入固定只读 n10s 查询。保留 PostgreSQL 发布/ACL、ERP 数据所有权；GraphConfig、Shapes 与验证范围必须有隔离和备份方案。本轮未实施标准语义适配。

R3 — P1（相对于用例 E）：销售出库问题缺少数据映射与业务规则契约​

位置：ERP ontology.py 的 RESOURCES/RELATIONS；service.py 的 SOURCE_PERMISSIONS；dto.py 的 Action/Metric。

当前固定资源覆盖 Supplier、Product、PurchaseOrder、PurchaseOrderItem、Customer、ProductCategory、ProductUnit，没有销售订单与库存资源/关系。Action 仅允许三个固定只读查询 executor，没有出库前置条件的业务规则模型。这里的属性约束不能回答“库存不足、状态未审核或其他原因是否阻止出库”。

现有脚本模型案例使用采购问题，工具调用与最终答案预先给定，能证明传输，不能证明本体改变了真实模型的工具选择或业务判断。不能把采购金额查询成功作为销售出库解释已验收。

建议：由 ERP 数据所有者提供获准的销售订单/库存固定映射、权限与只读诊断工具；明确规则的真实来源，再做两 Provider 与无本体的真实模型对照。本轮未新增业务能力。

R4 — P2：读取一个发布版本会加载最多 100 份历史正文​

位置：service.py，versions 104–113 行；runtime.py，authorized_snapshot 24–28 行、search 135–164 行。

versions(..., definitions=True) 查询全部 Version 列，只按 network_id 过滤并 LIMIT 100，之后 Python 才选实际发布版本。SQL 构造探针确认：

{'selects_definition': True, 'limit': 100, 'filters_exact_version': False}

describe 开始和结束各调用该路径；_finish 又重复 authorize/network，search 则最多处理 50 个网络，命中结果还逐项重新取目录。切到 Neo4j 后，仍先读取 PostgreSQL 整份模型，再读 Neo4j 整份模型。这不是按相关对象查询图。

单版本正文上限 256 KiB；100 个接近上限的历史版本，单网络一次就可能搬运约 25 MiB 序列化正文，另有解码/Pydantic 开销。search 的总 I/O 会继续放大；这不是“50 个网络同时常驻内存”的实测结论，也未测得 OOM。

建议：运行时按 network_id/version/status 精确获取当前发布行；历史列表保持独立。保留最终授权/来源复验，去掉同一复验内的重复查询，不能用跨请求权限缓存换性能。真实实例可用后记录 EXPLAIN 与每阶段耗时。本轮未优化生产查询。

R5 — P2：累计图读取预算可被最后一次调用越过​

位置：providers.py，load 95–106 行及 retrieval_budget 134 行。

代码只在下一次 load 之前判断已消耗时间。剩余预算不会传给 Driver，最后一次读取完成后也不检查。因此 1 秒预算、两次各 0.75 秒的读取，仍成功返回：

one-second graph budget accepted: 1.5

探针替换单调时钟与图传输，不进行 sleep 或数据库访问。每个事务有 timeout，不能由此推导整个工具调用也有相同硬截止时间；连接池获取、多个事务以及网络失联还需分别考虑。Agent 默认 MCP timeout 为 10 秒，也不等于服务端同步工作立即取消。

建议：明确区分单事务 timeout 和整次检索 deadline，将剩余预算传到读取事务，并在结果交付前复核截止时间；保持连接/超时的显式回退记录。不能只增加外层 asyncio.timeout 就认为线程内 SDK 调用已被取消。本轮未修复。

Agent、Provider 与 Langfuse 实际链路​

用户消息 → api.load_mcp_tools → 已授权 Nacos/MCP 工具目录
  → harness 的本体使用说明 → DeepAgents 自主选择（尚无真实模型效果证据）
  → mcp_tools.guard 再验注册契约/委托
  → Backend MCP 验签 → anyio worker → ontology.agent_tools.invoke
  → Tenant UoW → runtime.authorized_snapshot / search
  → PostgreSQL 发布指针/Schema + 当前 ERP catalog + Knowledge 来源
  → provider_request / load
      Legacy: 已授权 PostgreSQL Schema
      Neo4j: 固定 READ → Element.payload → 相同 OntologySchema
  → 权限过滤 → describe 的 build_context → MCP text/structuredContent
  → adapter 转成 ToolMessage → 下一次模型调用 → 回答

查询按工具调用发生，不预先整图注入 System Prompt。build_context 有字符上限及 UTF-8 字节的保守 Token 上界，后者不是实际模型 usage；query/traverse 的数据结果仍走原预算。缓存只在单个工具/HTTP 请求内，search→describe→query 会分别取快照，没有跨工具内容去重。整个 Run 不持久锁定 Provider；每次工具都选择并记录实际模式和回退，不能称为 Run 全局固定。

Action 映射现有固定只读查询 executor，不执行图中脚本、SQL、URL 或模型自造工具。目录先按当前 scope/RBAC/模块权益筛选，Agent 工具清单不会由本体授予新权限；不应把“本体定义 Action”误写成“本体实现动态工具发现授权”。新旧 Provider 目前提供相同语义，未证明 Neo4j 比 Legacy 提升关系理解或业务判断。

观测复用现有 delegation 后的 traceparent、Backend metadata OTLP 与 Agent Langfuse stage adapter。代码存在 resolve_provider/retrieve/build_context/inject_context/fallback/query；新的 provider 枚举、数量与版本字段能经过 stage 和 Langfuse 的共享白名单，不会因独立 metadata 过滤器而全部丢失。未发现为本体新增第二套根 Trace。

限制：没有逐 Cypher/APOC/n10s 调用 Span；当前也没有 APOC/n10s 业务调用。实际 Token 归属、标准规则遵循和最终答案引用未由本体 evaluator 验证。inject_context 在 MCP handler 返回时打点，只证明交付到 adapter，不保证后续 checkpoint/压缩/模型成功，更不证明回答正确。本轮 InMemory 测试通过，没有可提交的真实 Langfuse Trace URL/ID。

现有 quality.compare 支持 2–5 个 variant，可复用 none/legacy/neo4j 对照；当前 Langfuse fixtures 明确是合成 replay，不是真实模型结果，也无本体语义的已核验金标准、关系/规则评分器。不要把现有 fixture 分数当作本体质量。
