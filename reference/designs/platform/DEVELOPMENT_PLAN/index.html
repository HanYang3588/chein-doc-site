Fast Vben Admin v1.0-v2.0 可落地实施计划

本文保留 v1.0–v2.0 的阶段计划和当时的验收记录。“2026-07-14 当前基线”是该日期的快照，不代表 2026-09-29 的运行状态。当前前端为 React web-pro；当前实现与剩余门禁见模块化实施基线和前端架构。

2. 实施目标​

本计划用于指导当前项目从“功能已基本成形”收口到“v1.0 可发布、可部署、可二次开发”的状态。

当前项目已经具备登录、用户、RBAC、菜单、部门、字典、参数、日志、文件、通知、站内消息、仪表盘、Items、OpenAPI、Docker 等基础能力。后续实施重点不是继续堆新模块，而是把这些模块做成稳定闭环：

  • 初始化数据稳定可重复。
  • 权限码、菜单、前端按钮和后端接口一致。
  • 页面体验一致，关键路径无阻塞问题。
  • API 契约稳定，生成类型可用。
  • 核心测试可持续运行。
  • Docker Compose 最小部署可验证。
  • 文档与实际实现一致。

3. 总体原则​

3.1 先收口，后扩展​

v1.0 只做后台基座必需能力，不实现岗位、对象存储、OAuth2、多租户、BPM、CRM/ERP/AI。

3.2 后端权限是最终边界​

所有管理接口必须由后端 require_permission("<permission_code>") 控制。前端菜单和按钮隐藏只做体验优化。

3.3 每个模块必须闭环​

模块完成定义：

  • 模型和迁移存在。
  • API 可用。
  • 权限码接入。
  • 默认菜单或入口配置完整。
  • 前端页面可操作。
  • 测试覆盖核心正向和越权场景。
  • 文档更新。

3.4 小步验证​

每个阶段结束必须运行本阶段验收命令。不得把构建、测试、部署问题留到最后集中处理。

3.5 不照搬 Litchi​

参考 Litchi 的成熟模块边界和页面组织，但当前项目以 FastAPI + React / Umi Max / Ant Design Pro 的后台基座为目标。Litchi 的平台级能力进入路线图，不进入 v1.0 阻塞范围。

17. 建议执行顺序​

原 M0-M6 作为 v1.0 历史验收基线保留。基于当前实现，后续按以下顺序推进：

  1. 近期收口除 Docker Compose 实机补验外已基本完成，优先保持文档、CI 和 generated 代码持续一致。
  2. 推进 v1.4 企业能力，先接入 Redis 和安全基线，再完成 OAuth2/SSO 与第三方登录闭环。
  3. v2.0 开始前必须先完成租户隔离 ADR 和数据迁移 POC，不能直接给现有表机械增加 tenant_id。
  4. BPM 作为独立技术选型和产品范围评审，不与多租户主链路强绑定。

  • Redis 故障行为经过测试，不能造成全站无提示超时。
  • OAuth2/SSO 使用协议测试和安全用例验收，不以“页面可配置”作为完成标准。
  • 至少一个第三方平台在测试环境完成真实回调登录。
  • 登录限流、验证码和 MFA 具备后台恢复路径。
  • OAuth2、社交登录、缓存和安全模块均有后端测试与关键 E2E。

建议周期：12-20 个工作日。

20. v2.0 平台化探索​

当前状态（2026-07-15）：ADR-0002 已接受，Tenant/TenantMembership、默认租户迁移、登录令牌与会话租户绑定已实现；平台租户管理、租户角色与组织初始化、租户停用、成员移除与默认成员关系修复、会话撤销、我的租户和顶栏安全切换已形成前后端闭环。用户、角色、RBAC、部门、岗位、UserPost、Items、字典、参数、文件、存储渠道、登录与操作日志、公告、站内信、短信和邮件均已加入租户隔离。租户内唯一约束、关联资源复合外键、缓存 key 和文件物理路径均携带租户上下文；跨租户列表、详情、更新、导出、配置引用、消息投递和私有文件 URL 已有自动化回归测试。租户套餐、成员数、文件数和存储容量配额已完成后端强制校验、用量查询和前端管理闭环，默认无限套餐保证历史行为兼容。

角色数据权限支持全部数据、本部门、本部门及下级、本人数据和自定义部门集合；多角色范围取并集，全局超级管理员显式旁路，无有效角色默认本人。Items 的列表、导出、详情、更新和删除，以及用户管理的列表、导出、详情和管理操作均在后端注入同一范围过滤；自定义部门关联使用租户复合外键阻断跨租户绑定。空库迁移到最新 head、初始化连续执行两次和 Alembic 模型差异检查已通过。

20.1 多租户前置 ADR​

多租户属于架构改造，开发前必须明确：

  • 租户隔离采用共享库共享表、共享库独立 Schema，还是独立数据库。
  • 租户识别来自域名、Header、Token claim 还是用户选择。
  • 超级管理员、平台管理员和租户管理员的边界。
  • 全局数据、租户数据和用户私有数据的分类。
  • 唯一索引是否由全局唯一调整为租户内唯一。
  • 缓存 key、文件路径、日志和消息如何携带租户上下文。
  • 历史数据如何归属默认租户以及如何回滚。

20.2 多租户实施阶段​

阶段内容退出标准
POC选择用户、角色、Items 三个模块验证隔离方案已完成：用户、角色、RBAC 和 Items 的跨租户查询、修改及错误角色绑定均被测试阻断
基础层租户模型、上下文、依赖、迁移和初始化已完成：请求绑定明确租户上下文，支持租户生命周期、初始化和安全切换
系统模块用户、角色、菜单、部门、岗位、字典、参数租户化已完成：系统数据按租户查询，code/key 改为租户内唯一，跨租户关联由复合外键阻断
业务模块文件、消息、日志和缓存租户化已完成：文件元数据与物理路径、存储渠道、公告与站内信、短信邮件、登录与操作日志及缓存 key 均按租户隔离
运营能力套餐、配额、租户启停和初始化模板已完成：租户启停、成员移除、会话撤销、套餐与配额、用量查询，以及可配置根部门和七类可选种子数据的初始化模板均已实现

20.3 数据权限​

当前状态：已完成。角色管理前端可配置五种范围和自定义部门；后端共享查询过滤器覆盖 Items 与用户管理关键入口，并已有五种范围、部门树、多角色并集、超级管理员旁路和跨租户自定义部门自动化测试。

  • 先支持全部数据、本部门、本部门及下级、本人数据和自定义部门集合。
  • 数据权限必须在后端查询层注入，不能只依赖前端筛选。
  • 超级管理员旁路规则必须显式且有测试。
  • 对导出、统计、批量操作和异步任务应用相同权限范围。

20.5 v2.0 退出标准​

  • 多租户隔离通过自动化越权测试和数据迁移演练。
  • 任意租户无法通过 ID 猜测、导出、搜索或文件 URL 访问其他租户数据。
  • 数据权限适用于页面、API 和导出。 建议周期：多租户与数据权限 20-35 个工作日。

21. 后续版本质量门禁​

每个版本合并和发布前至少执行：

cd D:\project\chein
pnpm backend:lint
pnpm backend:test
pnpm generate:api
pnpm frontend:typecheck
pnpm frontend:build
pnpm frontend:pro:test

同时满足：

  • Alembic 从空库升级到 head 成功。
  • Alembic 从上一个发布版本升级到 head 成功。
  • 初始化脚本连续执行两次无重复数据。
  • Docker Compose 核心服务健康检查通过。
  • 新增外部服务均有超时、重试边界、脱敏和不可用降级测试。
  • 新模块至少包含一个管理员正向 E2E 和一个普通用户越权 E2E。
  • 不允许用 README 声明、菜单存在或页面可打开替代功能验收。

22. 下一迭代建议​

下一迭代继续完成 v2.0 多租户系统与业务模块，建议任务顺序：

  1. 为后续新增的批量操作和业务模块持续补齐数据权限安全测试。
  2. 在具备 Docker CLI 的环境完成 Docker Compose 核心服务健康验收。
