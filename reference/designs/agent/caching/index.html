Agent 对话与工具结果缓存设计

状态：Proposed（模型网关基线采用 Higress AI Cache，配置尚未落地）

适用范围：Higress 模型响应缓存、工具结果缓存、并发请求合并、失效和观测

本文是 Agent 缓存策略的唯一事实源。缓存只用于减少重复模型调用、工具调用和响应 延迟，不是 Run、RunEvent、Checkpoint、Snapshot 或权限判断的事实源；删除缓存后 必须仍能得到正确结果。

1. 当前情况和结论​

项目模型网关基线采用 Higress。当前工作区还没有 Higress 部署和 ai-cache 插件配置， QWEN_BASE_URL 仍指向模型服务地址；因此本文按目标态设计，接入前必须先补齐网关配置。

缓存职责划分如下：

  1. 模型响应缓存：使用 Higress 官方 ai-cache 插件，通过 Redis 做精确缓存。
  2. 工具结果缓存：使用 Higress 官方 response-cache 插件缓存内部 ERP Facade 响应； 数据所有者负责定义哪些 Tool 可以缓存、缓存键和 TTL。
  3. 并发请求合并：使用 Agent/Redis 短期锁，Higress 两个缓存插件都没有 singleflight 能力。
  4. 模型 Prefix/KV Cache：只在自部署模型时评估，当前通过 Qwen 兼容 API，不适用。

首期只启用精确匹配，不启用语义缓存。金额、权限和时间范围查询不能接受近似问题命中。

缓存类型实现位置默认作用域首期策略
Model Response CacheHigress ai-cache + Redis租户 + 有效数据范围首先实现精确缓存
Tool Result CacheHigress response-cache + Redis租户 + 有效数据范围与模型缓存分开配置
In-flight CoalescingAgent / Redis与模型缓存键相同第二期实现
Semantic CacheHigress + Embedding + Vector DB近似问题默认关闭
CheckpointAgentThread恢复执行，不是缓存

2. Higress 缓存的硬边界​

Higress 提供两个适合本项目的官方缓存插件：

  • ai-cache：缓存 LLM 结果，支持 OpenAI 协议、流式和非流式响应。
  • response-cache：缓存普通 HTTP 响应，支持从请求头或请求体提取缓存键。

两者都支持 Redis、cacheTTL、cacheKeyPrefix 和跳过缓存头：

  • LLM 缓存使用 x-higress-skip-ai-cache: on。
  • 工具响应缓存使用 x-higress-skip-response-cache: on。
  • 两者默认 cacheTTL=0 都是永不过期，必须显式设置有限 TTL。

插件不知道本项目的租户、RBAC、仓库授权、Policy 或数据版本，因此不能直接把用户问题 交给插件生成缓存键。缓存键必须由 Agent 在完成授权后计算：

  • ai-cache：把组合键放入 OpenAI Chat Completions 标准字段 user，配置 cacheKeyFrom: user。
  • response-cache：把组合键放入请求头 x-chein-cache-key，配置 cacheKeyFromHeader: x-chein-cache-key。

x-chein-cache-key 是内网头，只能由 Agent 在完成授权后生成；BFF 必须丢弃或覆盖 浏览器传入的同名 Header。缺少合法缓存键时按 skip 处理，不能退回按 URL 缓存。

user 的值是服务端 HMAC 后的一次性缓存标识，不包含用户原文、问题原文或仓库名称。 接入前必须确认 Qwen 兼容接口接受并忽略该不透明值；如果供应商拒绝、改写或将其作为 模型语义输入，则不得开启跨用户缓存，改为只在用户范围内缓存或关闭 Higress 缓存。

3. 缓存键​

Higress 最终使用的 Redis Key 是：

<cacheKeyPrefix><cacheKeyFrom 提取的值>

ai-cache 的组合键至少包含：

组成作用
key version组合键格式变化时自动 miss
tenant + data scope fingerprint隔离租户、权限、所有者和仓库范围
question hash + context hash当前问题、历史消息和摘要
tool result hashERP 查询参数、Snapshot、数据修订和 source_as_of
model + model config hash模型版本、Thinking 和生成参数
prompt + toolset + policy versionPrompt、工具集合和策略版本
response options语言、输出格式、深度思考和图表开关
time bucket当前日期、月份和历史时间窗口

response-cache 的组合键至少包含：

组成作用
key version + Tool code/version缓存格式和工具版本
tenant + data scope fingerprint隔离租户、权限、所有者和仓库范围
normalized args hash查询类型、日期、粒度和过滤条件
policy + dataset version授权和指标口径版本
data revision / source_as_of + time bucket数据新鲜度

输入规范化只统一空格、大小写、全角/半角和等价标点，不删除否定词、数字、日期、 实体名或条件词，也不做同义词改写。规范化规则必须版本化。

模型缓存要求同一租户、相同有效数据范围、相同问题、上下文和 ToolResult；工具缓存 要求相同 Tool、参数、数据版本和授权范围。不同租户、权限、仓库范围、工具结果或 模型/Prompt 版本必须 miss。数据范围指纹未建立前，缓存键必须包含 user_id，不能与 同租户其他用户共享。

4. Higress 模型响应缓存​

目标 Higress 配置示例：

enableSemanticCache: false
cacheKeyStrategy: lastQuestion
cacheKeyFrom: user

cache:
  type: redis
  serviceName: chein-agent-cache.dns
  servicePort: 6379
  username: chein-agent
  password: "<deployment secret>"
  database: 1
  cacheKeyPrefix: "chein-agent:prod:qwen:"
  cacheTTL: 60
  timeout: 1000

这里的 lastQuestion 只是 Higress 选择 cacheKeyFrom 的策略名，实际缓存键完全来自 Agent 写入的 user 组合值，不是直接使用用户最后一句问题。

规则：

  1. cacheTTL 必须显式设置，不能用默认值 0，默认值表示永不过期。
  2. Redis 使用独立 database、ACL 和内存预算，不复用 RBAC/登录限流 namespace。
  3. cacheKeyPrefix 按环境和模型区分，模型或 Prompt 版本变化时组合键也必须变化。
  4. 当前 Agent 使用流式模型调用。必须用 cacheToolCallsFrom 对齐 Qwen 的实际 SSE tool_calls 路径并验证检测有效；只有不含 ToolCall 的最终文本响应才允许缓存。 如果无法可靠识别 ToolCall，工具调用阶段必须通过跳过缓存头禁用缓存。
  5. 最终回答基于工具结果时，组合键必须包含 ToolResult/Snapshot hash，不能只用用户问题。
  6. Agent 明确禁止缓存的请求使用 x-higress-skip-ai-cache: on；浏览器和模型不能控制该头。
  7. Higress 命中响应使用 model:"from-cache" 和零 Token usage 模板。LangChain 适配器 必须能够正常解析；Token 成本统计需要单独记录命中数或节省量。

首期不维护第二套 Agent 最终回答缓存，避免和 Higress 双写、双失效。未来如果需要在 模型调用前直接完成整个 Run，才评估 Agent 级结果缓存，不能把它和 Higress 缓存混用。

5. 工具结果缓存​

工具调用不是 LLM 响应，不能交给 ai-cache；目标是给 Backend ERP Statistics Facade 增加一条 Higress 内部路由，并挂载官方 response-cache 插件。它缓存的是 HTTP 响应， 不是 ToolCall 消息。

cacheKeyFromHeader: "x-chein-cache-key"
cacheResponseCode: [200]
cacheValueFromBodyType: "application/json"
cacheValueFromBody: ""       # 空值表示缓存完整 JSON 响应体

cache:
  type: redis
  serviceName: chein-agent-cache.dns
  servicePort: 6379
  username: chein-agent
  password: "<deployment secret>"
  database: 1
  cacheKeyPrefix: "chein-tool:prod:erp-statistics:"
  cacheTTL: 60
  timeout: 1000

规则：

  1. Agent 完成委托上下文和参数校验后，生成 x-chein-cache-key HMAC 组合键。
  2. 组合键包含 Tool code/version、参数、租户、有效数据范围、Policy version、数据修订 和时间窗口；未建立数据范围指纹时包含 user_id。
  3. 返回值必须带 generated_at、source_as_of 和适用的数据版本。
  4. 没有数据版本或 source_as_of 时只能短 TTL，不能长期共享。
  5. 只缓存整数 200 响应；403、404、422、5xx 和降级响应不缓存。
  6. 大结果只缓存摘要和 Artifact 引用，不能把无上限明细放入 Redis。
  7. 命中时 Higress 返回 x-cache-status: hit，Agent 可记录 tool.cache.hit；未命中为 miss，跳过为 skip。
  8. 数据写入、审批或反审核必须改变 data_revision 或时间窗口；没有修订号时只用短 TTL。

response-cache 不知道 Tool 语义和租户权限，数据所有者必须声明哪些 Tool 可以缓存、 缓存键包含哪些字段以及 TTL。不能只按 URL 或请求体缓存 ERP 统计。

命中工具响应缓存时请求不会到达 Backend，因此不会再次执行 Tenant UoW/RLS。只有当前 请求已经完成授权，且缓存键包含数据范围指纹、Policy version（或未建立指纹时包含 user_id）时才允许命中。若产品要求权限撤销立即生效，必须关闭该响应缓存，或使用 版本化失效和足够短的 TTL。

查询建议 TTL原因
含今天、当前月或当前年的统计30-60 秒新审核单据会改变结果
已结束的历史日期范围5-15 分钟仍可能反审核或补录
当前日期工具不缓存每次结果都会变化

TTL 不能超过数据所有者声明的数据新鲜度。如果 Facade 后续返回可靠 data_revision， 应优先用修订号，TTL 只做兜底。

6. 并发请求合并​

Higress ai-cache 和 response-cache 当前都没有 in-flight 合并：两个同时到达的 冷启动请求可能都 miss。 如果需要严格只执行一次模型：

  1. 所有请求先完成权限和数据范围校验。
  2. 使用同一组合键在 Redis 申请短期锁。
  3. one leader 执行模型和工具，follower 等待最终结果。
  4. leader 成功后由对应的 Higress 插件写入 Redis，再唤醒 follower。
  5. leader 失败、超时或锁失效时，follower 回退正常执行。

私有回答只能合并同一用户的请求；同租户共享只有在数据范围指纹可用且共享模式开启 时才能合并。锁必须有过期时间，follower 超时不能返回空结果或缓存成功状态。

7. 失效、删除和降级​

  1. 模型、Prompt、Tool、Workflow、Policy 或 Contract 版本变化时，组合键自然 miss。
  2. 数据版本变化时，ToolResult hash 变化并自动 miss。
  3. RBAC、模块权益或数据范围变化时，组合键中的 scope/version 变化。
  4. 没有可靠版本时只依赖短 TTL，不宣称强一致。
  5. 租户、用户或 Thread 删除时必须覆盖对应缓存数据和索引。

禁止用全库 SCAN 清理业务缓存。使用有限 TTL、按租户/环境区分的 key prefix 和必要 索引。高敏感或个人信息必须加密或禁止缓存；普通租户业务数据至少要有 Redis ACL、 短 TTL 和禁止跨用户复用。Higress 或 Redis 不可用时回源模型，不能改变 Run 状态和 权限语义。

8. 观测​

Higress ai-cache 的 AI 日志提供 cache_status：

  • hit：网关缓存命中，未调用后端模型。
  • miss：未命中，继续请求模型。
  • skip：通过 x-higress-skip-ai-cache 跳过且不缓存。

Higress response-cache 在工具响应头返回 x-cache-status: hit|miss|skip，Agent 工具 可以据此写 tool.cache.hit 事件，但不得把缓存键、ERP 原始行或完整响应写入 RunEvent。

至少采集命中率、miss、skip、缓存延迟、后端模型调用数、缓存 TTL 和 Redis 错误。日志 不得记录拼接后的原始缓存键、问题、Prompt、ToolResult 或模型完整回答。

当前 ai-cache 不提供来源 Run ID。RunEvent 默认只记录模型调用事件；如果需要“本次 Run 由 Higress 缓存命中”的业务级审计，需要扩展插件响应头/日志并通过 Trace 关联， 不能在 Agent 中伪造 source_run_id。

9. 分阶段实施​

  1. H0：部署 Higress、Redis 独立 database/ACL，配置 ai-cache 和 response-cache， 但先关闭缓存。
  2. H1：只缓存单轮、无工具、同一用户的模型精确响应，enableSemanticCache: false。
  3. H2：通过 response-cache 缓存同一用户的 ERP Statistics 响应，只缓存 200， 短 TTL，并记录 x-cache-status。
  4. H3：组合键加入 Snapshot、ToolResult、数据版本和时间窗口，支持同一数据范围内 不同用户复用。
  5. H4：确有并发重复请求后，再增加 Redis 短期锁和请求合并。
  6. H5：语义缓存继续默认关闭；只有非权威、可人工核对的场景才单独评审。

10. 验收标准​

  1. 同租户、同数据范围、同问题、同上下文的重复请求命中 Higress Redis。
  2. 不同租户、权限、仓库范围、ToolResult 或数据版本必然 miss。
  3. 模型、Prompt、Toolset、Policy 或 Contract 版本变化必然 miss。
  4. cacheTTL 为非零，缓存不会永久驻留。
  5. 真实 Qwen 流式 tool_calls 响应不被 ai-cache 缓存；最终回答包含工具结果哈希。
  6. 相同 Tool 参数和同一用户命中 response-cache；403、422 和 5xx 不缓存。
  7. response-cache 的 x-cache-status 能正确写入 hit、miss 或 skip。
  8. x-higress-skip-ai-cache 和 x-higress-skip-response-cache 同时跳过读取和写入。
  9. Higress/Redis 故障时回源模型或 ERP Facade，授权仍失败关闭。
  10. 模型命中响应可被 LangChain 正常解析，零 usage 不污染真实成本统计。
  11. AI 日志不记录原始问题、Prompt、ToolResult 或完整回答。
  12. 删除或权限变化后，相关缓存按 TTL、组合键或索引失效。

11. 开源方案对比​

Star、最近活动和许可检查日期：2026-09-14。Star 只用于初筛，接入前仍需核对版本、 许可证、CVE、维护状态和数据边界。

项目Star最近活动 / 许可缓存能力结论

选择结论：模型响应缓存采用 Higress ai-cache；工具结果缓存采用 Higress response-cache；两者共用独立 Redis。请求合并按需使用 Redis 短期锁。LiteLLM、 Portkey、Bifrost、GPTCache 不作为当前实现依赖。

12. 待决项​

  1. 确认 Qwen 兼容接口对自定义 user 字段的接受、透传和安全策略。
  2. 确认 Qwen SSE tool_calls 的实际路径和 cacheToolCallsFrom 配置。
  3. 确认 Higress 插件版本、Redis 独立实例/database 和连接凭据来源。
  4. 确认 cacheTTL、key prefix、最大响应大小和日志保留期限。
  5. 如果需要 Run 级命中审计，确认插件响应头或日志关联方案。
  6. 语义缓存是否允许只用于非权威说明；默认答案仍然是不进入首期。
